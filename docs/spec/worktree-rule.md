# worktree の運用規約(ba0918-worktree)

## 目的

版管理の worktree(1 つのリポジトリに、ブランチごとの作業ディレクトリを複数ぶら下げる仕組み。
git では `git worktree`)は、複数のエージェントが同じリポジトリを並行して変更するための
基本の道具になった。ところが運用の決まりがないまま使うと、エージェントやツールごとに
流儀が分かれて散らかる。運用の中で、プロジェクトやエージェントごとに worktree が
思い思いに作られ、散らかっていることが問題になった。散らかりは次の形で現れる。

- 置き場所がツールごとに違う。リポジトリ内のツール専用ディレクトリ、リポジトリの兄弟
  ディレクトリ、ホームディレクトリ配下が混在し、どこに何があるかを誰も把握していない
- 名前がツールの自動生成(ランダムな単語の組み合わせなど)のまま残り、どのタスクの
  作業場所かが名前から分からない
- 作業が終わっても片付けられず、マージ済み・放棄済みのブランチの worktree が溜まる。
  ディレクトリだけを消すと、版管理側の登録が残骸として残る
- 同じ worktree に 2 つの書き手が入る、worktree の中のセッションが本体のチェックアウトを
  書き換える、といった隔離の破れが起きる

原因は、ツールがそれぞれの既定で worktree を作り、どこにも共通の決まりがないことである。
この規約は、ツールに依らない共通の決まりを「置き場所・名前と起点・隔離・終わり方」の
4 点で定める。ツールの既定がこの規約と違うときは、ツールの設定をこの規約に合わせる。

## 発火条件

ルーティングのメタデータは `ba0918-routing: required:worktree` を宣言する。
生成される AGENTS.md のルーティング表に `worktree` の行として現れ、worktree を作る・入る・
片付ける作業のときに読まれる。

発火させる場面:

- worktree を作る、または作るかどうかを決める
- 並行する書き手に作業場所を割り当てる
- 既存の worktree に入って作業する
- worktree を片付ける、または溜まった worktree を棚卸しする

`always` にはしない。worktree を使わない作業にまで読ませる理由がないため。
ルーティングなし(description による発火だけ)にもしない。ツールが自動で worktree を作る
場面では、エージェントが「worktree の作業をしている」と自覚しないまま進むことがあり、
description の発火だけでは読まれない恐れが大きい。AGENTS.md の表に行を出して名指しする。

## 対象

版管理の worktree を使う作業すべて。人がエージェントに頼んで作らせたもの、エージェントが
自分の判断で作るもの、ツールが並行実行のために自動で作るものを区別しない。

ツールの設定方法、worktree を作る・消すための自動化スクリプトやフックは扱わない。
それらはワークフロー側の持ち物である(`repository-design.md` の役割分担)。

## 規範

各節の合格条件は、SKILL.md の必須ルールの節がその規範を述べていることを指す。

### 1. 置き場所

- worktree の置き場所は、リポジトリごとに 1 つのディレクトリに決める。
- 既定は、リポジトリのルート直下の `.agents/worktrees/`。プロジェクトの文書が別の場所を
  宣言していれば、そちらに従う。
- 置き場所のディレクトリは、リポジトリの ignore ファイルで除外する。除外するのは
  `.agents/worktrees/` そのものでよく、そのために `.agents/` 全体へ除外を広げない。
  `.agents/` の下を追跡対象として使うツールがあるためである。プロジェクトが別の理由で
  `.agents/` 全体を既に除外しているなら、それで満たされる。
- ignore ファイルを読まないツール(型検査、テストランナー、ファイル監視など)の
  走査対象からも、置き場所を外す。
- ツールの既定の置き場所がこれと違うときは、ツールを設定して合わせる。設定できないツールが
  作った worktree も、この規約の名前・隔離・終わり方の規範には従わせる。
- worktree の中に worktree を作らない。

`.agents/` を選ぶ理由: 特定のツールやモデルの名前を含まず、複数のエージェントが共有する
作業状態の置き場所として使われ始めている名前だからである。ツール名入りのディレクトリ
(あるツール専用の隠しディレクトリの下など)を既定にすると、そのツールを使わない
エージェントにとって置き場所が恣意的になり、統一の根拠を失う。

リポジトリ内に置く理由: リポジトリと一緒に見つかり、リポジトリと一緒に消える。
兄弟ディレクトリに置くと、親ディレクトリに作業中のブランチ名が並び、別のリポジトリの
作業クローンと区別がつかなくなる。親ディレクトリの一覧は、ba0918-secrets が
「このリポジトリより広い範囲の出力」として扱うものでもある。
代償は、ignore を読まないツールの走査除外が要ることで、これを規範に含めた。

合格条件: 上の 6 点と既定の場所が述べられている。
反例: 「worktree はリポジトリの兄弟ディレクトリに作る」を既定にする。
反例: worktree のためだけに `.agents/` 全体を ignore するよう指示する。

### 2. 名前と起点

- 1 つの worktree は、1 つのブランチと 1 つのタスクに対応させる。
- worktree のディレクトリ名は、ブランチ名から導く(区切り文字の置き換えだけで対応が
  分かる形にする)。
- 名前はタスクを表す。ツールが自動生成した名前(ランダムな単語、連番、ツール名だけの接頭辞)
  を残さない。ブランチ名の形式そのものはプロジェクトの慣習に従う。
- 起点は明示して選ぶ。既定は、取り込み直したリモートの基底ブランチである。
  未 push の作業の上から切るときは、そうしたことを報告に書く。
- 終わったタスクの worktree を、別のタスクに使い回さない。新しいタスクには新しい worktree を
  作る。

合格条件: 上の 5 点が述べられている。
反例: ツールが付けた `bright-running-fox` のような名前のまま worktree とブランチを残す。

### 3. 隔離

- 同時に書き込む主体 1 つにつき、作業ツリーを 1 つ割り当てる。本体のチェックアウトも
  作業ツリーの 1 つとして数える。
- 2 つの書き手に、同じ worktree で同時に書き込ませない。
- worktree で作業するセッションは、本体のチェックアウトや他の worktree のファイルを
  変更しない。
- 読むだけの調査には worktree を作らない。
- worktree は新しいチェックアウトとして扱う。依存関係はその中で導入し、ignore 済みの
  設定ファイルは必要なものだけを写す。書き込まれる共有資源(ビルド出力のディレクトリ、
  ローカルのデータベース、待ち受けポート)を worktree 間で共有しない。
- 他の主体がかけた worktree のロックを外さない。

合格条件: 上の 6 点が述べられている。
反例: 並行する 2 つの実装役に、同じ worktree を割り当てる。
反例: 本体の依存ディレクトリへのシンボリックリンクで worktree の依存を済ませる
(一方の更新が他方を壊す)。

### 4. 終わり方

- 成果を worktree の外へ届けてから作業を終える。届けるとはコミットしてリモートへ push する
  ことを指す。push しない場合は、残す理由とブランチ名を報告する。worktree の中にしかない
  成果を、完了として報告しない。
- ブランチがマージされた、または放棄されたら、その worktree を片付ける。
- 片付けは版管理の worktree 削除操作で行う。ディレクトリを直接消さない。直接消した
  残骸が版管理に登録されたまま残っていれば、版管理の操作で登録を掃除する。
- 未コミットの変更や未 push のコミットを含む worktree を、承認なしに強制削除しない。
  ブランチの削除も、マージ済みでなければ承認を取る。どちらも取り消せない。
- 版管理の worktree 一覧を台帳として扱う。一覧に載るすべての worktree に、進行中のタスクが
  対応している状態を保つ。対応するタスクがないものは、上の手順で片付けるか、
  持ち主に確かめる。

合格条件: 上の 5 点が述べられ、強制削除とブランチ削除の承認は SKILL.md 本体に置かれている
(安全に関わる即応部分なので `references/` へ移さない)。
反例: 「不要になった worktree はディレクトリごと削除する」。

### 5. 報告と記録での指し方

- worktree は、リポジトリのルートからの相対パスかブランチ名で指す。絶対パスを追跡対象の
  ファイル・コミットメッセージ・外に出す文に書かない。

これは ba0918-secrets の「作業クローンの絶対パス」の規範と重なる。worktree は既定で
リポジトリ内にあるため相対パスで指せる、という当てはめを書いておくことに意味があるので、
スキル間の重複として許す(`skill-authoring-rule.md` 規範 4)。

合格条件: 上の 1 点が述べられている。

## 判断と例外

- 書き手が 1 つしかいない作業では、worktree を作らず本体のチェックアウトで作業してよい。
  worktree は並行のための道具であり、作ること自体が目的ではない。
- 実行環境がセッションごとに使い捨てのクローンを用意する場合(クラウド上の隔離環境など)、
  そのクローンが既に隔離の単位になっている。その中でさらに並行する書き手が要るときに
  限って、この規約で worktree を作る。
- ツールが worktree を自動で作り自動で消す場合、置き場所と名前の規範は設定で満たせる
  範囲で満たす。終わり方の規範(外へ届けてから終える、承認なしに強制削除しない)は、
  ツールが自動で消す場合も変わらない。

合格条件: SKILL.md の判断基準の節が、上の 3 点を述べている。

## 既存スキルとの境界

- ba0918-commit: コミットの分け方とメッセージ。この規約は worktree の中でのコミットの
  仕方を扱わず、「外へ届けてから終える」という終わり方だけを定める。
- ba0918-delegation: 役割の契約と委譲の情報の流れ。実行手段は意図的に定めていない。
  この規約は、委譲された書き手が並行するときの作業場所の割り当て方を定める。
  委譲の仕方そのものは扱わない。
- ba0918-secrets: 絶対パス・隣のクローンの一覧など、実行環境の情報の露出。
  規範 5 の 1 行だけを当てはめとして重ねて書く。

統合しなかった理由: `skill-authoring-rule.md` 規範 1 の基準(領域が違う、または読まれる
作業の種類が違う部分は別スキルに分ける)を、上の 3 スキルそれぞれに当てた。

- delegation には入れない。worktree は委譲なしでも使う(人が並行セッションを開く、
  ツールが自動で作る)ため、読まれる作業が一致しない。また delegation は実行手段を定めない
  設計である。
- commit には入れない。領域はコミットの中身であり、作業場所のライフサイクルは別の領域である。
  仕様の反例「コミット規約にリリースのタグの打ち方を同居させる」と同じ形になる。
- secrets には入れない。worktree 固有の露出の規範は既にある規範の当てはめにすぎない。
  常時読まれるスキルに足すと、worktree を使わない作業すべての読み込み量が増える。

## リポジトリへの組み込み

- `skills/ba0918-worktree/SKILL.md` を追加する
- README と README-ja のスキル表に 1 行(Loaded by 列は `required:worktree`)
- CHANGELOG の Unreleased に追加の記載
- `repository-design.md` の「初期スキル」表に 1 行
- `.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の description に、
  同じ文字列で worktree の運用を足す。plugin.json の keywords に `worktree` を足す
- このリポジトリの AGENTS.md のルーティング表に `worktree` の行を足す

バージョンの bump はリリース時にまとめて行うので、この仕様の範囲に入れない。

## 受け入れ確認

- 人による確認: SKILL.md を、この仕様の各節の合格条件と 1 つずつ突き合わせる
- 既存チェッカー: `python3 scripts/validate.py` と pytest、CI の skills-ref が通る

## 作らないもの

- 特定のツールの設定方法、worktree を作る・消すスクリプトやフック
- ブランチ名の形式(接頭辞の体系など)。プロジェクトの慣習に委ねる
- コミットの分け方やメッセージの規則の再掲

## 却下

- 既存スキル(delegation / commit / secrets)への統合 — 上の「統合しなかった理由」
- リポジトリの兄弟ディレクトリを既定の置き場所にする — 親ディレクトリが散らかり、
  別リポジトリのクローンと区別がつかず、親ディレクトリの一覧が露出の経路になる
- 特定ツールの既定ディレクトリを既定の置き場所にする — ツールを使わないエージェントに
  とって根拠のない場所になり、統一の効果を失う
- 置き場所の既定を決めず「プロジェクトが宣言する」だけにする — 宣言のないプロジェクトで
  ツールごとの既定に戻り、散らかりが解消しない
- worktree のために `.agents/` 全体を ignore させる — `.agents/` の下を追跡対象として使うツールと衝突する
- `always` のルーティング / ルーティングなし — 「発火条件」の節
