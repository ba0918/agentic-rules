# 人間向け成果物の可読性ルール

## 目的

コード作成、調査、レビューなどを行う AI が、人間に内容を理解させないまま
承認だけを求める状態を防ぐ。

文章を短く整えること自体は目的ではない。技術的な情報と不確実性を保ったまま、
読者が何を伝えられたのか自分の言葉で説明できる状態を目指す。

## 対象

このルールは、人間が読むすべての出力へ適用する。

- 会話上の応答と質問
- 調査報告とレビュー結果
- 仕様書、計画書、説明文
- 承認や判断を求める表示
- 長い成果物をどこへ、どのように提示するか

内容が正しいか、証拠が十分か、その結論へ同意すべきかは別に判断する。
人間へ判断を求める条件も、このルールでは決めない。
このルールは、必要な判断を理解できる形で提示する責任だけを持つ。

## 想定読者

既定の読者は、考える力はあるが対象分野には詳しくない初学者とする。

読者が次の情報を知っていると仮定しない。

- プロジェクト内部だけで使われる言葉
- 過去の調査や会話の経緯
- 今は提示されていない文書
- コード内の名前や仕様の条項番号が表す意味

読者が貼り付けた文章に専門用語が含まれていても、その用語を理解している
証拠にはしない。読者が自分の言葉で使っているか、説明不要と明示した場合は、
その対話で理解済みの言葉として扱える。

読者の知識を低く見積もることと、読者の思考力を低く扱うことを混同しない。
論点、根拠、条件、不確実性は削らない。

## 情報を減らさず翻訳する

要約と翻訳を区別する。

要約は、目的に合わせて情報を選び、詳細を省く。
翻訳は、元の情報を保ったまま、読者が意味を理解できる言葉へ組み直す。

詳細な説明を求められている場面で、要約を翻訳の代わりにしない。

技術的な観測結果は、読者が次の関係を理解できるように書く。

- 実際に何が起きたか
- それにより何が困るか
- なぜ起きたか
- 何が確認済みで、何が未確認か
- 根拠をどこで確認できるか

この並びは固定の見出しではない。文章の内容に合わせて段落や箇条書きを選ぶ。
必要のない見出しを埋めることや、同じ結論を言い換えて繰り返すことはしない。

## 用語の扱い

一般に意味が定着し、文脈上の意味も明らかな技術用語は、そのまま使ってよい。
すべての技術用語へ辞書的な説明を付ける必要はない。

次の言葉は、普通の言葉による説明の代わりに使わない。

- その場で作った言葉
- 略語
- プロジェクト固有の名前
- コード内部の識別子
- 文脈により意味が変わる言葉

まず具体的に何が起きるかを書く。内部実装との対応が必要な場合は、そのあとで
用語や識別子を示す。

同じ成果物内ですでに意味を示した言葉は、意味が変わらない限り説明を繰り返さない。

## 外部参照の扱い

仕様の条項番号、ファイルの場所、コード内の名前、ログは、根拠を確認するための
参照として残す。

ただし、参照先を開かなければ本文の意味が成立しない書き方にはしない。
本文だけで主張を理解でき、そのあと必要に応じて根拠へ辿れる状態にする。

## 質問と選択肢

選択肢だけを提示しない。判断する場所に、少なくとも次の文脈を置く。

- 何を判断するのか
- なぜその判断が必要なのか
- 選択により何が変わるのか

互いに影響する判断を、全体像のない一問一答へ分断しない。
関連する判断は、関係を理解できる単位で対話する。

質問へ説明を足すだけでは不十分な場合もある。人間の判断が不要な事項まで
選択肢にすると、説明が丁寧でも承認は儀式になる。
人間へ判断を求める必要性は、その作業を担当する別の規則に従う。

## 提示場所と情報量

読者が内容を読む場所と、判断や操作を行う場所を離しすぎない。

表示範囲が限られる場所では、後半が見えないことを前提に重要な情報を配置する。
長い成果物は、読むのに適した文書として提供する。会話へ同じ全文を複製し、
大量のスクロールを要求しない。

短さは合格条件ではない。長くても意味を追える文章はある。
短くても文脈のない選択肢や、専門用語だけの断片は読めない。

## 不足している情報

確認できていない情報を、自然に見える推測で埋めない。

たとえば、新旧を同じ条件で比較した結果がなければ、どちらが優れているかは
判断できない。その事実を平易に説明する。

読みやすさによって、証拠不足や未確認事項を隠してはならない。

## 対比例

悪い例:

> test identity は保存されるだけで再計算されず、GREEN event が受理される。

この文章では、内部用語を知らないと何が問題なのか分からない。

良い例:

> 失敗を確認したときのテストと、修正後に成功したテストが同じ内容か確認していない。
> そのため、失敗したテストを必ず成功する内容へ差し替えても、修正成功として扱われる。
> コードでは、このテストの対応関係を `test identity` と呼んでいる。

後者は技術的な事実を削らず、内部用語を知らなくても問題を理解できる。

## 合格条件

最終的な合格条件は、想定読者が成果物の言葉をそのまま復唱するのではなく、
何を伝えられたか自分の言葉で説明できることとする。

毎回、実際の読者へ理解度の確認を求めてはならない。それ自体が新しい儀式になる。

スキルの検証では、過去に読解上の問題が起きた事例から固有名詞と機密情報を除き、
同じ種類の依頼を独立した読み手へ与える。その結果について、次を別々に確認する。

- 読み手が、何が起き、なぜ問題かを説明できる
- 書き換えによって、元の技術的主張、条件、不確実性が失われていない
- 本文から仕様、コード、検証結果へ辿れる
- 証拠不足が、流暢な説明によって隠されていない

文字数、文の長さ、見出し数、専門用語数は、問題を疑う手掛かりには使える。
それらの数値だけを合格条件にはしない。
