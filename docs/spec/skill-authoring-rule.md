# スキル執筆の規約(ba0918-skill-authoring)

## 目的

スキルを書き続けると、読み込みコストの抑え方、特定の実行環境に縛られない書き方、
後から直しやすい構造といったノウハウが溜まる。これまでそのノウハウは、
このリポジトリの設計仕様(`repository-design.md`)の中に、このリポジトリ自身の決まりとして
書かれていた。この規約は、そのうち一般化できる部分を、どのリポジトリでスキルを書くときにも
使える規範として 1 つのスキルにまとめる。

外部(モデル提供元など)のスキル作成ガイドラインは、モデルが新しくなるたびに更新されうる。
それに依存すると、放置したときに規範が古びる。そのためこの規約は、外部の記述を引用せず、
モデルの世代が変わっても成り立つ考え方だけを抜き出して自分の言葉で定める。
ソフトウェア設計の原則も、考え方が応用できるものに限って取り入れる。原則の名前は出さない。
名前を出すと、その原則の一般的な解釈が持ち込まれ、ここで意図した意味からずれるからである。

## 発火条件

ルーティングのメタデータ(`ba0918-routing`)は持たない。使う場面がスキルの執筆に限られ、
そのときだけ読まれればよいので、ルーティング表には載せず、description の発火だけで読ませる
(前例: `ba0918-testing`)。

発火させる場面:

- 新しいスキルを書く
- 既存スキルの SKILL.md や `references/` を書き換える
- スキルを分割・統合する

発火させない場面:

- スキルを使うだけのとき
- スキルを監査・評価するとき

合格条件: SKILL.md の frontmatter に `ba0918-routing` がなく、description が上の 3 場面を
使う場面として挙げ、使うだけ・監査評価の場面を使う場面として挙げていない。
反例: description が「スキルの品質を評価するときにも使う」と書いている。

## 対象

Agent Skills 形式のスキル(SKILL.md と `references/`、同梱スクリプト)に限る。
AGENTS.md・スラッシュコマンドなど、スキル以外の指示文書は対象にしない。

規則を述べる規範スキルと、副作用を伴う手順を実行する手続き型スキルの両方を対象にする。
片方にしか当てはまらない規範には、どちらに当てはまるかを明記する。

既存スキルを部分的に書き換えるときは、書き換えた箇所にだけ規範を当てはめる。
スキル全体を規範に合わせることは求めない。

合格条件: スキル本文の適用範囲の節が、対象を Agent Skills 形式のスキルに限ると述べ、
部分的な書き換えでは書き換えた箇所にだけ当てはめると述べ、
片方の種類にしか当てはまらない規範すべてに、その種類が書かれている。
反例: 手続き型スキルにしか意味のない「副作用を実行してよい条件」の規範が、
種類の指定なしに全スキル向けとして書かれている。

## 規範

各節の合格条件は、書かれたスキル(ba0918-skill-authoring 自身)の本文がその規範を
述べていることを指す。

### 1. 適用範囲と境界

- 1 つのスキルは 1 つの領域を扱う。
- 本文の最初に適用範囲の節を置き、扱うことと扱わないことを書く。扱わないことのうち、
  隣のスキルが担うものは、そのスキルを名前で示す。これはすべてのスキルに求める。
- スキルが膨らんだときは、領域が違う部分、または別の種類の作業で読まれる部分を
  別スキルに分ける。同じ領域の中で特定の状況にしか要らない部分は別スキルにせず、
  規範 2 に従って `references/` へ移す。

合格条件: 本文が上の 3 点を述べ、別スキルに分ける基準を「領域が違う、または読まれる作業が違う」
として示している。
反例: コミット規約のスキルに、リリース時のタグの打ち方を節として同居させる
(作業の種類が違うので別スキル)。コミット規約のスキルに、秘密情報が漏れたときの対応手順を
references/ として持たせる(コミット中に起きるが領域は秘密情報の扱いなので、
その領域のスキルの `references/` に置く)。逆に、秘密情報の扱いのスキルから
漏洩対応の手順を別スキルに切り出す(同じ領域の特定状況なので `references/`)。

### 2. 読み込み量の管理

- 分量は「読まれる頻度あたりのコスト」として扱う。数値の上限は規範にしない。
  適切な上限はモデルや用途で変わり、陳腐化するからである。
- SKILL.md には、そのスキルが読まれるすべての場面で要る内容だけを置く。
- 特定の状況でしか使わない内容は `references/` に置き、SKILL.md にはその状況と
  読むべきファイルを書く。
- 安全に関わる即応部分(まず報告する、不可逆操作の前に承認を取る、など)は、
  手順を `references/` へ移すときも SKILL.md に残す。

合格条件: 本文が上の 4 点を述べ、行数などの数値上限を規範として書いていない。
反例: 事故対応の手順全体を `references/` へ移し、SKILL.md から「まず報告する」も消す。

### 3. 実行環境に縛られない

- 本文は、特定のツール・モデル・実行環境のコマンドに依存した書き方をしない。
- 他のスキルはパスではなく名前で参照する。参照先が入っていない環境でも壊れず、
  単に読まれないだけにするためである。スキルのディレクトリの外を指すパス参照はしない。
  スキル内部の `references/` への相対参照は許す。
- 特定の実行環境でしか意味を持たない frontmatter の項目は書いてよい。ただし、その項目を
  無視する環境でもスキルが正しく機能し、本文がその項目の効果を前提にしないこと。
- 同梱スクリプトについては、必要な実行環境(言語ランタイムやコマンド)を SKILL.md に
  明記することだけを求める。スクリプトの書き方は扱わない。

合格条件: 本文が上の 4 点を述べている。
反例: 本文の手順が「このスキルはツール制限の項目で書き込みを禁じているので、
書き込みの確認は不要」と、特定環境の frontmatter の効果を前提にしている。

### 4. 変更に強い構造

- 新しい状況には、既存の規則を書き換えるのではなく、節や `references/` を足して対応する。
- 既存の規則の意味を変えるときは、意味が変わる変更だと明示する。言い換えに紛れ込ませない。
- 他のスキルや文書から参照されうる見出し・識別子(スキル名、節の名前など)は軽々しく変えない。
- スキル間での規則の重複は許す。スキル単体が配布単位であり、共有原典への依存は
  原典 1 箇所の変更が全参照スキルへ無審査で波及する事故を招くからである。
  1 スキル内では、同じ規範を 3 箇所以上に書いたら統合する。規則・理由・手順は役割が違うので
  再掲してよいが、規則の丸写しは別の役割ではない。

合格条件: 本文が上の 4 点を述べ、重複の扱いをスキル間とスキル内で分けて書いている。
反例: 2 つのスキルで同じ規則を書いているのを重複だとして、規則を共有文書 1 つに括り出し、
両スキルがそれを読む形にする(共有文書 1 箇所の変更が両スキルへ無審査で波及する)。

### 5. 発火の書き方

- description には発火の判断材料だけを書く: 何の領域のスキルか、どの作業・状況で使うか、
  利用者が実際にそのスキルを呼ぶときに使う言葉。
- 本文にある規則の中身・条件・手順は description に書かない。領域を表すキーワードを
  並べるのは、発火の手がかりになるので許す。
- 例外: 手続き型スキルの、副作用を実行してよい条件は「いつ使うか」の一部として
  description に書く(規範 6)。
- 言語は指定しない。利用者が実際に使う言葉を入れる、という規範から、
  利用者の言語のキーワードが自然に入る。

合格条件: 本文が上の 4 点を述べ、許す例と禁じる例を対比で示している。
反例(禁じる側): description に「各層を決まった順で探し、最初に成立した段で止まり、
理由を 1 行で記録する」と規則そのものを書く。許す側は「reuse-before-build:
layer decomposition, search ladder」のような領域語の列挙。

### 6. 規則の種類ごとの書き方

- 一律に短く書くことはせず、規則の種類で文体を選ぶ: 禁止・必須は 1 行 1 命令、状況で変わる判断は理由と適用条件、
  誤解されやすい境界は対比例。
- 重要度は、大文字・「絶対に」・同じ指示の繰り返しといった強調ではなく、
  理由と適用条件で示す。
- 完了や確認の条件は「〜したか?」という自問ではなく、観測できる証拠(コマンドの出力、
  差分、ファイルの存在など)を求める形で書く。
- 規範スキルには、本文の構成順として 適用範囲 → 必須ルール → 判断基準と例外 → 対比例 →
  完了時の証拠 を推奨する。手続き型スキルの構成順は、適用範囲を最初に置くこと以外は定めない。
- 手続き型スキルは、副作用を実行してよい条件を本文と description の両方に書く。
  description による発火と、副作用の実行許可は別物だからである。
- 手続き型スキルの副作用は、その作業自体を明示的に頼まれたときだけ実行し、
  ほかの作業のついでには実行しない。

合格条件: 本文が上の 6 点を述べ、手続き型スキルにだけ当たる規範にその旨が書かれている。
反例: 確認ゲートを「テストが通ったことを確認したか?」と書く
(求めるべきはテストの出力)。

## 既存スキル・文書との境界

- `ba0918-design`(コード設計の原則)とは別物として書く。コード向け原則の翻訳という
  位置づけにはしない。
- スキルの検証・評価(発火率の測定、実行品質の測定、回帰検査など)は扱わない。責務が違う。
- 人間向けの文章の可読性は `ba0918-readability`、情報の置き場所は `ba0918-placement` の担当。
- ルーティング表のルールを 1 つの文脈で 1 回読めば有効とする規約と、委譲先の読み直し免除は、
  スキルの書き方ではなくルールの読み方の規約なので、このスキルに入れない。
  置き場所は現状(`repository-design.md` と `ba0918-scaffold` が生成する AGENTS.md)のまま。

## repository-design.md との分担

一般化できるスキル執筆の規範は、この仕様書(`skill-authoring-rule.md`)を正本にする。
SKILL.md はこの仕様の実装であり、規範を変えるときは、このリポジトリの spec-first の規約どおり
この仕様書を先に直し、SKILL.md をそれに合わせる。`repository-design.md` からは
この仕様書を参照する。

`repository-design.md` の 4 節の振り分け:

- 「執筆スタイル」: 本文は英語・description は英語 + 日本語キーワード、規範スキルの構成順
  (下記)、「SKILL.md は 500 行以内」を残す。それ以外(一律に短くしない、規則の種類ごとの文体、観測可能な証拠を求める
  確認ゲート)はこの仕様書へ移し、参照を置く
- 「SKILL.md と references/ の分担」: 「500 行は壊れないための上限であって予算ではない」と、
  ルーティングの種類ごとに読まれる範囲(`always` は全セッション、`required:<工程>` はその工程の
  全作業)の説明を残す。それ以外はこの仕様書へ移し、参照を置く
- 「スキル自己完結の原則」: 共有原典の実害の経緯(claude-skills で共有文書 1 変更が 10 スキルに
  影響)と、共有原典方式へ移るまでの段階を残す。
  名前参照・ディレクトリ外パス参照の禁止・`references/` 内の相対参照の許可・スキル間重複の
  許容とスキル内重複の統合はこの仕様書へ移し、参照を置く
- 「手続き型スキルの実行条件」: 見出しは残し(節の名前で参照されうる)、中身はこの仕様書を
  参照する 1 行にする

このリポジトリ側に残る決まり全体(上の 4 節以外の節を含む。命名規約の節は今回編集しない):

- スキル名の `ba0918-` 接頭辞と命名規約
- 本文は英語、description は英語 + 日本語キーワード
- 規範スキルの本文の構成順は 適用範囲 → 必須ルール → 判断基準と例外 → 対比例 → 完了時の証拠
  を必須とする(一般規範では推奨)
- SKILL.md は 500 行以内
- ルーティングのメタデータ(`always` / `required:<trigger>`)
- ルーティングの種類ごとに読まれる範囲の説明
- 共有原典の実害の経緯、共有原典方式へ移るまでの段階

合格条件: 上の 4 節から、この仕様書へ移すとした規範の本文が消え、代わりにこの仕様書への参照があり、
残すとした決まりは残っている。「手続き型スキルの実行条件」の見出しが残っている。
反例: `repository-design.md` の「執筆スタイル」節に、強調ではなく理由で重要度を示す規範が
この仕様書と並んで書かれている(どちらかだけ直されてずれる)。

## リポジトリへの組み込み

- `skills/ba0918-skill-authoring/SKILL.md` を追加する
- README のスキル表に 1 行(Routing 列は `fires from its description`)
- CHANGELOG の Unreleased に追加の記載
- `repository-design.md` の「初期スキル」表に 1 行
- README の「Skill document structure」節の「Every `SKILL.md`」を、規範スキルに限る記述に直す
  (`ba0918-scaffold` はこの順になっていない)
- README 冒頭の領域の列挙に、スキル執筆を足す
- `.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の description に、
  同じ文字列でスキル執筆(skill authoring)を足す
- PROJECT.md の Glossary に Procedural skill と Triggering を足し、Rule skill の項の
  「Only rule skills belong in this repository」を、scaffold のメタスキルも置くと読める形に直す
  (この仕様と同時に変更済み)

バージョンの bump はリリース時にまとめて行うので、この仕様の範囲に入れない。

## 受け入れ確認

- 人による確認: 新しい SKILL.md を、この仕様の各節の合格条件と 1 つずつ突き合わせる
- 既存チェッカー: `python3 scripts/validate.py` と
  `npx --yes skills-ref@0.1.5 validate skills/ba0918-skill-authoring/` が通る

この規範を機械的に検査するルールはバリデータに足さない。規範の多くは判断を含み、
機械検査にすると要件の文面を固定するだけの検査になるからである。

## 作らないもの

- 外部(モデル提供元など)のガイドラインの引用や、それを出典とする記述
- スキルの検証・評価の規範
- ソフトウェア設計原則の名前(SOLID・DRY など)の使用
- AGENTS.md・スラッシュコマンドなど、スキル以外の指示文書への適用
- 既存スキルをこの規範に合わせる修正(別の作業として扱う)
- 文脈ごとに 1 回読む規約・委譲先の読み直し免除を、このスキルに入れること

## 却下

- `ba0918-create-skill` という名前 — 命名規約はドメイン名詞で、create は動詞
- `ba0918-skill-design` という名前 — `ba0918-design` と取り違えやすい
- `always` / `required:skill-authoring` のルーティング — 使う場面が限られ、ルーティング表に常駐させる必要がない
- 分量の数値上限 — 適切な値がモデルや用途で変わり、陳腐化する
- 本文・description の言語の指定 — 利用者の言葉を入れる規範で足り、言語の固定はリポジトリ固有の決まりに属する
- 手続き型スキルの構成順の規定 — 自分たちの運用実績からまだ蒸留できていない
- この規範の機械検査 — 判断を含む規範を文面の固定検査に落とすことになる
