# Rust の規約(ba0918-rust)

## 目的

Rust のコードを書く作業が増えた。Rust 用の指示を何も与えずにエージェントに書かせた
2 つのリポジトリ(kotowari、kakoi)を 2026-10-04 に調べると、次が見つかった。件数は
clippy の lint を 1 つずつ有効にして数えた(テストのコードを除く)。

- **古い edition を既定に選ぶ。** kotowari は edition 2021 で生成され、人が指示して 2024 に
  直した。kakoi は `rust-version = "1.88"`(2024 edition が使える版)を宣言しながら、
  今も edition 2021 のまま。モデルは学習データに多い古い版を、確かめずに書く。
- **lint が関門になっていない、または既定の lint だけ。** kotowari はフックにも CI にも clippy が
  無かった。kakoi は CI で `-D warnings` を掛けていたが既定の lint だけで、`unsafe` ブロック
  83 件に SAFETY の注記が無かった(注記のあるものは 71 件。慣習はあったが守らせる仕組みが無い)。
- **自前の enum への `_ =>`。** kotowari で約 21 件(自前の `Item`・`Block`)、kakoi で 21 件
  (自前か外部かは未仕分け)。変種を足してもコンパイラが漏れを教えない。ba0918-design の
  「網羅的な match」が Rust では効いていない。
- **文字列のエラー。** `Result<_, String>` が kotowari で 14 件、kakoi で 23 件。呼び出し側が
  エラーの種類で分岐できず、テストは文言の一致に頼る。
- **理由の無い unwrap / expect。** kotowari で 26 件、kakoi で 61 件。大半は実際には落ちないが、
  なぜ落ちないかが書かれていない。
- **ライブラリの中の出力。** kotowari のライブラリ(kotowari-core)に `println!` が 43 件。
  出力が戻り値ではなく標準出力でしかテストできない。
- **MSRV とツールチェーンの不揃い。** kotowari は 3 クレート中 1 つだけが `rust-version` を
  宣言し、ツールチェーンは固定されていない。kakoi は workspace で 1 回宣言し、CI の MSRV ジョブで
  その版のビルドを確かめていた(良い例)。

逆に、よく「AI の書く Rust の悪い癖」として挙がるもの — `Arc<Mutex<T>>` の乱用、実装が 1 つの
trait、`lazy_static!` のような古い書き方、`todo!()` の残り — は、どちらのリポジトリでも
見つからなかった。一般論の一覧をそのまま規則にすると、規則の半分は外れ、読み込みのたびに
何も変えない文を読ませることになる。

この規約は、上の実害から逆算した規則に絞る。そして各規則を、可能な限り lint という機械の検出に
結びつける。人やエージェントの注意に頼る規則は、kakoi の SAFETY 注記のように、守られる所と
守られない所が混ざる。

## 発火条件

ルーティングのメタデータは `ba0918-routing: required:rust` を宣言する。
生成される AGENTS.md のルーティング表に `rust` の行として現れる。

発火させる場面:

- Rust のコードを書く、直す、レビューする
- Cargo の manifest、ワークスペース、ツールチェーン、lint、整形の設定を作る・変える
- Rust のクレートやワークスペースを新しく作る、edition や MSRV を上げる
- 依存クレートを足す・上げる

`always` にはしない。Rust を使わないプロジェクトに読ませる理由がない。
ルーティングなし(description による発火だけ)にもしない。「ちょっと直す」作業では
description が発火しないことがあり、そのときに古い edition や文字列のエラーが入る。
表に行を出して名指しする。Rust を使わないプロジェクトでも行は生成されるが、
「rust の作業のとき」という条件なので読まれない。

## 対象

Rust に固有の形: 版の選び方、manifest とワークスペースの宣言、関門(整形・lint・テスト)、
lint の抑え方、エラーと panic、網羅的な match、unsafe、所有権と型、ライブラリの副作用、
今の書き方、依存の足し方、未完成の印。

扱わないもの:

- 設計原則そのもの(ba0918-design)。この規約は、その原則が Rust ではどの形になり、
  どの lint で守らせるかだけを書く。関数やモジュールの大きさ(kakoi で 100 行を超える関数が
  12、最長 447 行)も design の領域で、ここでは扱わない
- テストの書き方(ba0918-testing)、テストを先に書く順序(ba0918-tdd)
- 変異テスト、cargo-mutants(ba0918-mutation-testing)
- CI の定義の書き方(ba0918-ci)。この規約は何を関門にするかを定め、ワークフローの書き方は ci に従う
- クレートを採用するか自作するかの判断(ba0918-reuse)
- async ランタイム、FFI、no_std、マクロの書き方。実際に書くプロジェクトが出たら references を足す

規範は Rust の言葉(Cargo、ワークスペース、edition、rustfmt、clippy)で書く。これらは Rust の
公式のツールチェーンで、この規約の領域そのものである。`skill-authoring-rule.md` 規範 3 の
「特定のツールに依存しない」は、スキルを読むエージェントの実行環境(特定のエージェントや
そのコマンド)に依存しないことを指し、規約の領域の道具を名指すことを禁じない。
ただし、具体的なコマンドと設定の書き方は references に置く(mutation-testing と同じ分け方)。

- `references/project-setup.md`: ワークスペースの manifest、ツールチェーンの固定、関門のコマンド、
  MSRV の確かめ方、edition の移行の手順。確認日つき
- `references/lints.md`: 規範ごとの lint の対応、群を丸ごと有効にしない理由、既存のコードへの入れ方
- `references/modern-idioms.md`: 古い書き方と今の書き方の対応表。各行に安定化した版

## 規範

各節の合格条件は、SKILL.md の必須ルールの節がその規範を述べていることを指す。

### 1. 版は記憶ではなく出所で選ぶ

- 新しいクレートには、その時点の最新の安定版 edition を使う。書く前に公式の出所で確かめる。
- 既存のクレートの edition を上げるときは、移行の道具で機械的に直し、その変更を他の変更と混ぜない。
- 依存クレートの版は、レジストリから取る(版を書かずに追加して、道具に今の版を選ばせる)。
  記憶にある版番号を書かない。
- 使う API は、その版の文書で存在を確かめる。std の API は宣言した MSRV で使えるかを確かめる。

数字(今は 2024 edition、1.99.0)は規範に書かない。数か月で古くなり、規則が古い設定を勧める
ことになる。references に確認日つきで置く。

合格条件: 上の 4 点が述べられ、版の数字が SKILL.md に無い。
反例: 「edition は 2024 を使う」と数字で書く(2027 edition が出たとき、同じ実害が起きる)。
反例: `serde = "1.0.100"` のように記憶の版を書く。

### 2. 一度だけ宣言して継承する

- ワークスペースでは edition、rust-version、lint の設定をワークスペースで 1 回宣言し、
  各メンバーは継承する。
- rust-version を宣言する。宣言したなら、CI でその版でもビルドして確かめる。
- ツールチェーンの版を固定し、上げるときは意図した変更として上げる。上げて増えた lint の
  指摘は、その変更の中で直す。
- lint の設定は manifest に書く。コマンドラインの引数だけに置かない。

合格条件: 上の 4 点が述べられている。
反例: クレートごとに edition や rust-version を書き、3 つのうち 1 つだけが宣言する(kotowari)。
反例: CI が浮動の stable を使い、新しい lint が無関係な PR を赤くする。

### 3. 関門

- 整形の検査、警告を失敗として扱う lint(ワークスペース全体、テストを含む全ターゲット)、
  ワークスペース全体のテストを、CI の必須チェックにする。フックは補助で、正本は CI。
- lint の群(pedantic、nursery、restriction)を丸ごと有効にしない。lint を 1 つずつ選ぶ。
  restriction 群は、互いに矛盾する lint を含むため群では使えない。
- 既存のコードに lint を足すときは、既存の該当箇所を同じ変更で直すか、理由つきの抑制に
  置き換えてから足す。警告のまま積み上げない。

kotowari で pedantic を丸ごと有効にすると 826 件の警告が出た。全部を関門にすると、
直す作業が本来の作業を押しのけ、結局関門ごと外される。

合格条件: 上の 3 点が述べられている。
反例: 既定の lint だけで `-D warnings` を掛けて関門とみなす(kakoi の SAFETY 注記の漏れ)。
反例: `clippy::pedantic = "deny"` を足す。

### 4. lint の抑え方

- lint を抑えるときは、満たされなかったら警告になる抑制(`expect`)を使い、理由を書く。
  理由の無い抑制と、満たされなくても黙る抑制(`allow`)を使わない。検出できる範囲は lint で
  守らせ、`allow_attributes` が検出しない内側の属性(`#![allow(...)]`)はレビューで確認する。
- 作業を終わらせるために警告を抑えない。

合格条件: 上の 2 点が述べられている。
反例: `#[allow(dead_code)]` を足して完了と報告する。

### 5. エラーと panic

- ライブラリは、失敗の種類ごとの変種を持つエラーの型を返す。`Result<_, String>` と
  型を消したエラーを、ライブラリの境界の内側に流さない。
- 型を消したエラーや文脈を足すエラーは、バイナリの最上位(表示する所)で使ってよい。
- テスト以外のコードで unwrap しない。起きないと言える不変条件の所では expect を使い、
  メッセージになぜ起きないかを書く。lint で unwrap を禁じ、テストでは許す。
- ライブラリは、呼び出し側が回復できる失敗で panic しない。

合格条件: 上の 4 点が述べられている。
反例: `fn parse(s: &str) -> Result<Self, String>`(kotowari で 14 件)。
反例: `serde_json::to_string(&x).unwrap()` を理由なしに書く。

### 6. 網羅的な match

- クレートが持つ enum への match に、ワイルドカードの腕を書かない。変種を列挙する。
- 外部の enum で、残りを無視するのが意図した振る舞いなら、ワイルドカードを使ってよい。
  ただし外部の enum に変種が足されたとき、黙って無視されることになると知った上で使う。
- 公開する enum に今後変種を足すなら、その enum に非網羅の印を付ける。

ba0918-design の「網羅的な match」の Rust の形である。lint(`wildcard_enum_match_arm`)は
外部の enum にも反応するので、自前の enum が多いクレートでは lint で、そうでなければ
レビューで守らせる。

合格条件: 上の 3 点が述べられている。
反例: 自前の enum `Item` への `_ => {}`(kotowari で約 21 件)。

### 7. unsafe

- unsafe が要らないクレートは、unsafe を禁じる(forbid)。
- 要るクレートでは、unsafe を小さなモジュールに閉じ込め、すべての unsafe ブロックに、
  なぜ安全かの注記を付ける。注記の欠落を lint で検出する。
- unsafe 関数の中の unsafe な操作も、unsafe ブロックで囲む。

合格条件: 上の 3 点が述べられている。
反例: 注記のある unsafe と無い unsafe が混ざっている(kakoi で 71 件と 83 件)。

### 8. 所有権と型

- 借用で済む所で clone しない。借用チェッカーを通すための clone は、所有の設計を見直す合図。
- 引数は、読むだけなら借用の一般的な形(`&str`、`&[T]`)で受ける。所有を受けるのは、
  保持するか消費するときだけ。
- 共有の可変状態(`Rc<RefCell<T>>`、`Arc<Mutex<T>>`)は、所有の構造を直せないと確かめてから使う。
- 意味の違う値には、素の `String` や整数ではなく専用の型を、真偽の引数には enum を使う
  (境界をまたぐ値と、取り違えると壊れる値に限る)。

合格条件: 上の 4 点が述べられている。
反例: コンパイルを通すために `.clone()` を足していく。

### 9. ライブラリの副作用

- ライブラリのコードは、標準出力・標準エラーに書かず、プロセスを終了させない。結果を値で返し、
  表示と終了はバイナリが受け持つ。ライブラリのクレートで出力の lint を有効にする。

ba0918-design の「副作用を domain に置かない」の Rust の形である。

合格条件: 上の 1 点が述べられている。
反例: ライブラリの関数が `println!` で結果を出し、テストが標準出力を捕まえる(kotowari-core で 43 件)。

### 10. 今の書き方

- std が同じことをするなら、古いクレートや古い書き方を使わない。対応表を references に置き、
  各行に安定化した版を書く。使う前に MSRV で使えるかを確かめる。
  置換では必要な API の契約も保つ。たとえば async trait は、dyn を使わなくても、返す Future の
  Send 保証が必要なら単なる async fn に置き換えられない。

合格条件: 上の 1 点が述べられ、references に対応表がある。
反例: MSRV が対応する版以上なのに `lazy_static!` や `once_cell` を足す。

### 11. 依存

- Cargo.lock をコミットし、CI ではロックファイルどおりに解決させる。
- 依存の機能の一部しか使わないなら、既定の機能を外して要る機能だけを有効にする。

合格条件: 上の 2 点が述べられている。

### 12. 未完成の印

- `todo!()`、`unimplemented!()`、`dbg!()` を残したまま完了と報告しない。lint で検出する。

合格条件: 上の 1 点が述べられている。

## 判断と例外

- **lint で守れるものを lint で守る。** 注意に頼る規則は、守られる所と守られない所が混ざる
  (kakoi の SAFETY 注記)。規則ごとに lint を対応させ、対応する lint が無いものだけをレビューに残す。
- **群ではなく 1 つずつ。** pedantic は有益なものと好みのものが混ざり、restriction は互いに
  矛盾する。群を有効にすると、直す作業が本来の作業を押しのける(kotowari で pedantic 826 件)。
- **ワイルドカードの lint は、自前か外部かで分ける。** 外部の enum を多く match するクレートでは、
  lint を有効にすると理由つきの抑制が並ぶ。そのときはレビューで守らせる。
- **専用の型は境界と取り違えに限る。** あらゆる値を包むと、包む・剥がすだけのコードが増える。
- **版の数字は references に、確認日つきで。** 規範に数字を書くと、規範そのものが古くなる。

合格条件: SKILL.md の判断基準の節が、上の 5 点を述べている。

## 完了時の証拠

- 整形の検査、lint(警告を失敗として扱う、全ターゲット)、ワークスペース全体のテストの出力
- 版を選んだなら、確かめた出所(公式の文書、レジストリ)と確認した日
- 抑制、unsafe、expect を足したなら、その一覧と各々の理由

合格条件: SKILL.md の証拠の節が上の 3 点を観測できる形で求めている。

## 既存スキルとの境界

- ba0918-design: 一般原則(失敗は戻り値で、網羅的な match、副作用を domain に置かない、
  関数とモジュールの大きさ)。この規約はその Rust の形と、守らせる lint を書く。原則を繰り返さない。
- ba0918-testing / ba0918-tdd: テストの書き方と順序。
- ba0918-mutation-testing: 変異テストと cargo-mutants。
- ba0918-ci: CI の定義の書き方。この規約は関門の中身(整形・lint・テスト・MSRV)を定める。
- ba0918-reuse: クレートを採るか自作するか。この規約は、採ると決めた後の足し方(版の取り方)を定める。

統合しなかった理由: `skill-authoring-rule.md` 規範 1 の基準を当てた。Rust の具体形は、
Rust を書く作業でだけ読まれる。design に入れると、Rust を使わないプロジェクトにまで
読ませる(design は `always`)。

## 受け入れ確認

- 人による確認: SKILL.md を、この仕様の各節の合格条件と 1 つずつ突き合わせる
- references の設定例を、空のワークスペースに置いて整形・lint・テストが通ることを確かめる
- 既存チェッカー: `python3 scripts/validate.py` と pytest、CI の skills-ref が通る

この規約を機械検査するルールはバリデータに足さない。

## 作らないもの

- Rust の入門、一般的なベストプラクティスの一覧(モデルが既に知っていて、実害の根拠が無いもの)
- async ランタイム、FFI、no_std、マクロの手引き(書くプロジェクトが出るまで)
- 言語ごとのスキルの共通の枠組み(TypeScript などが要るようになったら、そのとき同じ形で足す)

## 却下

- `ba0918-lang-rust` という名前 — 命名規約の「短い一般語 1〜2 語」に `ba0918-rust` が合う
- 「AI が書く Rust の悪い癖」の一般的な一覧を規則にする — 2 つのリポジトリで半分が見つからなかった
- 版の数字(edition 2024、1.99)を規範に書く — 古くなる。references に確認日つきで置く
- clippy の群(pedantic など)を丸ごと関門にする — 「判断と例外」
- `always` のルーティング / ルーティングなし — 「発火条件」の節
