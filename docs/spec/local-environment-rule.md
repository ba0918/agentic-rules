# 実行環境の規約(ba0918-secrets 追記)

## 目的と出典

運用中の事故が出典である。エージェントが計画文書に作業クローンの絶対パス
(`/home/<アカウント名>/...` の形)を書き、それを公開リポジトリにコミットして公開した。
ba0918-secrets は読まれていた。コミット前に「認証情報の形をした文字列」の走査も
実施され、正しく無検出だった — パスは提示によってアクセスを与えないため、認証情報の
検査には掛からない。掛かるべきだった後半の宛先境界の規範が、適用されなかった。
(出典の事故は、本規約自身の「私的な作業が公開の変更の動機になるときは、構造の教訓を
残して同一性を落とす」に従い、リポジトリ名・アカウント名を伏せて形だけを記す。)

適用されなかった原因は、規範の側の 3 つの欠落である。

1. **機密文脈の模型が「持ち込み」だけを想定していた。** 認識表の行はすべて、より狭い
   出所から**運ばれてきた**材料である — 内部コードネーム、内部ホスト名、顧客名、
   機密文書からの引用、第三者著作物。それに作用する規範は「宛先の読者と**出所の**読者を
   比べよ」と書かれている。`pwd` で読み取った絶対パスには出所文書が無い。比較の
   一方の被演算子が存在しないので、規範が起動しない。事故はこの通りに起きた —
   後半全体が「機密文書と社内名の話」として読まれた。
2. **パスに言及する唯一の行が、ネットワークの行に入っていた。**
   `| 内部ネットワーク名 | 非公開ホスト名、内部ドメイン、内部 URL とパス |` の
   「内部 URL とパス」は、見出しに引かれてサーバ側のパスとして読める。OS のアカウント名・
   ホームディレクトリ・開発機のホスト名・作業クローンの絶対パスは、どの行にも無かった。
3. **証拠条件に捕まえる項目が無く、最も近い項目は当たらない一覧に依存していた。**
   「送出文が綺麗」は「作業ツリー外に置いた私的識別子の**一覧**に対する検索」を要求する。
   自分のアカウント名を私的識別子の一覧に書く者はいない — それは持ち込んだ材料ではなく、
   走っている場所の周辺的事実だからである。

同じ欠落を追って本文を通しで見ると、絶対パス以外に 2 つ出た。どちらもコミットが運ぶ
**メッセージ以外の欄**である — author と committer の同一性、そしてツールが足す trailer。
規範の対象面は「セッションが書く成果物」と定義されていたため、git や周辺ツールが
*埋める*欄はそこに入っていなかった。本リポジトリの履歴では、個人を特定するアドレスの
コミットと forge の no-reply 形式のコミットが混在し、コミットログには非公開セッションの
URL が複数載っている。どちらも認識表にも証拠条件にも無く、絶対パスと同じ理由で通り抜けた。

メタデータは内容より直しにくい。メッセージは後から書き直せるが、author・committer・trailer
はコミットを作った瞬間に固定され、直すにはコミットそのものの書き換えが要る。パスが
「コミットするな」で足りるのに対し、こちらは「作るな」の位置に門を置く必要がある。

走査を入れたことで、走査が捕まえない残りも見えた。実行環境由来の情報は、絶対パスの形を
していなければ素通りする — 作業クローンの親ディレクトリの一覧、他のクローンの棚卸し、
環境のダンプ。いずれも接頭辞を持たない素の名前の列で、非公開の作業が存在することと、
それが誰のための作業かを開示しうる。出典の事故と同じ振る舞い(エージェントが自分の
作業環境をコミットされる文書に書く)の一歩横であり、振る舞いとしては実証済みで、
違うのは文字列の形だけである。

## 判定基準

この分類は、他の機密文脈と異なり**形が固定**である。`/home/`、`/Users/`、
`/mnt/<ドライブ>/`、Windows のユーザプロファイル、先頭の `~/` — 機種をまたいで短い
定数集合に収まる。したがって判定は判断ではなく検索で行える:

- 追跡対象のファイル・コミットメッセージ・送出文に、実行機由来の絶対パスが無いこと
- 位置はリポジトリ直下からの相対パスで指されていること
- 残る出現は、明らかに偽のプレースホルダか、規則自身が示す検索パターンだけであること

一覧の正しさに依存しないので、初回から成立する。これは本リポジトリの validator が
スキル内リンクに対してすでに持つ判定(`OUTSIDE_TARGET_PREFIXES`・Windows ドライブ)と
同じ形の検査であり、対象を差分に広げたものである。

メタデータの側も同じく形が固定で、判定は push しようとしている範囲に対して行える:

- author と committer が、その宛先の読者が出所の読者より多くを知る形になっていないこと。
  個人を名指すアドレスは越える。すでにその読者へ公開している識別子は越えない
  (forge の no-reply 形式は、これを満たす通例の手段であって要件ではない)
- trailer が、その読者が見たことのない作業をその読者に指し示していないこと。
  読者が到達できない識別子は、その作業がセッションで行われたという以上を明かさない

どちらも `git log` の書式指定で読めるので、証拠は主張ではなく出力になる。

名前の列だけは形が固定でないので、走査では判定できない。判定は出所で行う:

- コミットされる文書に貼った出力が、このリポジトリより広い範囲のコマンドから来ていないこと
- 広い範囲から来ている場合は、このリポジトリに関係する部分だけを書き写し、出所を添えて
  いること

「この文章はどの範囲のコマンドが出したか」は読めば分かるので、一覧を持たずにレビューで
当てられる。一覧で塞ぐのは筋が悪い — 非公開の名前を一覧に集約するのは守りたいものを
1 箇所に集める行為であり、leak-response が一覧を作業ツリー外に置けと言う理由そのものが
そこにある。

## 既存規範との関係

「宛先の読者と出所の読者を比べよ」は残す。本規約はその一般形を別行で加える —
出所文書が無いとき、宛先の読者だけで判定する。既存行の改稿は意味変更(BREAKING)に
触れるため、追加のみとする。第二の原則としては扱わない: アカウント名も内部ホスト名も、
場所と人を特定するという点で同じ露出であり、柱は宛先比較のまま一つである。

Judgment の「名前はアクセスを与えないが、それでも露出する」とは連続している。
ただしあの段は「宛先比較は手で当てる。走査するものは無い」と締めており、本分類だけは
形が固定なので走査が効く。その差を明記して並べる — 例外ではなく、唯一の走査可能な分類
として位置づける。

ba0918-placement との重複は無い。placement は情報の**帰属先**(How/What/Why/Why not)を
決める規範であり、本規約は**読者の境界**を越えるかを決める。環境固有の事実を
セッション局所の作業状態か委譲文に置くという行は、置き場所の指定ではなく、
追跡対象から外すという露出防止の帰結である。置き場所が secrets なのはそのためである。

references/leak-response.md の再発防止(手順 4)も併せて直す。あそこは識別子を
「一覧に載せる」ことだけを制御として認めていたが、形が固定な識別子は一覧ではなく
走査で捕まえる。あわせて、記録の置き場所の条件を明記する — 次の変更がステージされる
場所で走らない記録は制御ではない。事故後に「メモリに残した」で終えられる余地を消す。

その保管先の条件そのものも誤っていた。当初は「作業ツリー外、またはリポジトリの
local-only exclude ファイル」を認めていたが、`.git/info/exclude` はクローンされない —
新しいマシン、新鮮なチェックアウト、CI はいずれもそれを持たずに始まる。制御が黙って
存在しない環境を許すので、条件は「新鮮なクローンを越えて残る場所」に改める。追跡対象に
しない要求と、クローンを越えて残る要求は両立する必要があり、それを満たすのは
リポジトリ外の場所か、リポジトリが配る ignore ファイルのどちらかである。

名前の列については、認識表の「内部識別子」の行がすでに非公開の作業のリポジトリ名を
挙げている。加えるのは分類ではなく、それが入ってくる経路である。Rules は「貼った出力」を
認証情報については対象に挙げているが(値をプレースホルダに置き換えよ)、範囲の広い出力
そのものを持ち込まないという規範は無かった。置換では足りない — 置き換えるべき「値」ではなく、
名前の列全体が露出だからである。

走査との関係は明記する必要がある。絶対パスの走査を入れた直後なので、実行環境の露出は
走査で済むと読まれうる。素の名前は形を持たないので走査は素通りし、ここは判断のまま残る。
コミット前に検索する規範ではなく、貼る瞬間に当てる規範である。

## ba0918-secrets への追記

Scope: 機密文脈の列挙に「セッション自身が走る環境」を加え、規範の対象面に
「計画と作業メモ」を加える。

認識表に加える行:

- 実行環境 | セッションが走るアカウント、作業クローンの絶対パス、ホームディレクトリ、
  機種のホスト名

認識節の締めに加える段: セッションが自分で作り出した材料も数える。機械から読み取った
アカウント名や絶対パスには出所文書が無いので、比べる狭い側が存在せず、宛先の読者だけで
決まる。

Rules に加える規範(3 行): 比較をセッション自身が書いた文にも当てる / 位置は
リポジトリ直下からの相対パスで指し、実行機由来の絶対パスは追跡対象のファイル・
コミットメッセージ・送出文のいずれにも置かない / 環境固有の事実はセッション局所の
作業状態か委譲文に置き、コミットされる文書には置かない。

Judgment に加える判断基準: 自分の環境も出所である。誰も渡していないので読者を持つ材料に
見えず、比較が当たらない。認証情報の走査も通る。同時に、ここだけは形が固定なので、
判断ではなく検索で捕まえられる。

Examples に加える対比: 実行場所を書き込んだ文書(Bad)と、リポジトリ直下を指す同じ指示
(Good)。

Evidence に加える項目: ステージ済み差分とコミットメッセージに対する絶対パス接頭辞の
検索。無検出、または明らかに偽のプレースホルダのみ。一覧を必要としない点を明記する。

メタデータの分については、Scope の対象面を「セッションが書く成果物」から「セッションが
書く成果物と、送出時に埋める欄」へ広げ、author と committer の同一性・trailer を名指しする。
認識表の実行環境の行に、版管理に設定された同一性と、ツールが足すセッション識別子を加える。
Rules には、メッセージ以外の欄を確認する規範と、同一性と trailer を同じ宛先比較で判定する
規範を加える。no-reply 形式は通例の手段として示し、要件としては書かない — 要件を手段で
書くと、利用側は手段の側を規則と読み、判定の側を読まなくなる。
Judgment には、メタデータが内容より直しにくい理由を 1 文で添える。Evidence には、push
しようとしている範囲の author・committer と trailer を `git log` の書式指定で読む項目を加える。

名前の列の分については、Rules に 1 行加える: リポジトリより広い範囲のコマンドの出力を、
コミットされる文書に貼らない。このリポジトリに関係する部分だけを書き写し、出所を添える。
Judgment には 1 文添える: 絶対パスの走査は素の名前の列を捕まえないので、この分は判断のまま
であり、当てる瞬間はコミット前ではなく貼るときである。Evidence は項目を増やさず、既存の
「私的文書から書いた箇所は出所を述べて読者を比べる」項目の対象に範囲の広いコマンド出力を
加える。証拠の種類が同じ(検索ではなく、出所を述べてレビューする)ためである。

## 適用範囲

既存リポジトリの履歴の棚卸しは要求しない。対象は、新たな変更が実行機由来の絶対パスを
新しく持ち出さないことのみである。既に刻まれた author・committer や trailer の訂正も
同様に本規約の対象外で、事故後の封じ込め(履歴書き換え・タグの打ち直し)と同じ扱いである —
references/leak-response.md の管轄であり、不可逆操作として人間の承認を要する。

description は日本語キーワードの追加のみとする(`絶対パス` `ユーザ名` `環境固有`)。
出典の事故ではスキルは正しく発火しており、発火は失敗点ではなかった — 失敗は読まれた後の
本文にあった。追加するのは、作業そのものがパスや環境の話として語られる場合の取りこぼしを
拾う分だけである。英文の発火条件は変更しない。
