# GUI の画面構成の規約(ba0918-gui-structure)

## 目的

GUI アプリの画面の作り方(部品の分け方、状態の持ち主、データとイベントの流れ、
描き直しの単位)に指針がないまま AI に実装を任せると、次のような形に崩れる。
実例として、ある非公開のデスクトップ GUI アプリでは次の症状が同時に出た。

- 最上位の画面の型 1 つに、数十の状態が集まった
- 十数個のファイルが、その可変状態を直接書き換えた
- 画面同士が互いの状態に手を入れた
- 1 つの変化でウィンドウ全体が描き直され、入力が引っかかった

この規約は、特定のフレームワークに依らない画面構成の一般則を定め、
AI が文脈なしに実装するときの基準と、レビューで突き合わせる基準の両方に使えるようにする。
フレームワークごとの実現方法、そのアプリの領域の一覧、ダイアログの優先順位といった
当てはめは、各プロジェクトの文書に置く。この規約には入れない。

一般則は、GUI 設計で知られた型(Passive View、画面の階層を 1 つの根から組む形、
Chain of Responsibility、Mediator、ステートマシン)を下敷きにしている
(参考: https://zenn.dev/nrs/articles/9ba91aea587bf5 )。型をそのまま採用せず、
型ごとに上の症状に効くかを見て、効く部分だけを規則にした。
スキル本文では型の名前を出さない。名前を出すと、その型の一般的な解釈
(型が持つ登場人物や実装の形)が持ち込まれ、ここで意図した意味からずれるからである。

## 発火条件

ルーティングのメタデータは `ba0918-routing: required:gui` を宣言する。
生成される AGENTS.md のルーティング表に `gui` の行として現れ、GUI のコードを設計・実装・
変更・レビューするときに読まれる。

発火させる場面:

- 画面・領域・ダイアログ・キーボード操作を足す、または変える
- 状態をどこに持つかを決める、または動かす
- ウィンドウ全体の描き直しや入力の引っかかりを直す
- GUI のコードをレビューする

`always` にはしない。GUI を持たないプロジェクトの作業すべてに読ませる理由がないため。

description だけの発火(ルーティングなし)にもしない。利用者は各プロジェクトの AGENTS.md の
ルーティング表からこのスキルを名指しして読ませる方針であり、ba0918-scaffold は
ルーティング表を手書きさせず、メタデータからだけ行を生成するため。

代わりに、このスキルを入れたプロジェクトには、GUI を持たなくても `gui` の行が生成される。
行は GUI の作業のときにだけ読ませるものなので、GUI のないプロジェクトでは読まれず、
害は表の 1 行に留まる。

合格条件: SKILL.md の frontmatter が `ba0918-routing: required:gui` を持ち、description が
上の場面を使う場面として挙げ、規則の中身を含まない。
反例: description に「状態の持ち主は 1 つ」「描画の中で状態を書き換えない」と規則そのものを書く。

## 対象

GUI を持つアプリの画面を組むコード。デスクトップ・Web・モバイルを問わない。

扱わないもの:

- 見た目(配色、レイアウトの寸法、アニメーション)とアクセシビリティ
- 特定のフレームワークでの実現方法(プロジェクトの文書に置く)
- 設計一般の原則(層の向き、純粋なドメイン、依存注入、型による検証)— ba0918-design
- テストの書き方の一般則 — ba0918-testing、テスト先行の手順 — ba0918-tdd

合格条件: 本文の適用範囲の節が、上の扱わないものと、フレームワークごとの当てはめは
プロジェクト側に書くことを述べ、隣のスキルを名前で示している。

## 規範

各節の合格条件は、SKILL.md の本文がその規範を 1 行の規則として述べ、
理由(判断基準の節)と違反の例(対比例の節)を持つことを指す。
規則ごとに理由と違反例を持たせるのは、レビューで規則と実装を 1 つずつ突き合わせる
基準として使うため。

### 1. 部品の構成

- 画面は、最上位の部品 1 つと、その下の領域ごとの部品で組む。
- 各部品は自分の描画を持つ。最上位がほかの部品の中身を描かない。

反例: 最上位の描画関数が、一覧・詳細・ステータスバーのすべての中身を 1 つの関数で描く。

### 2. 状態の持ち主

- どの状態にも持ち主は 1 つだけ。
- 保存される状態と、複数の領域にまたがる状態は、アプリの状態(ドメイン層)が唯一の持ち主で、
  UI の中でそれを持つのは最上位だけ。
- 保存されず 1 つの領域の中だけで使う状態(スクロール位置、選択中の行、検索欄の文字など)は、
  その部品が持つ。

反例: 選択中の項目を最上位と一覧の部品の両方が持ち、片方だけ更新されてずれる。
一覧の部品のスクロール位置を最上位が持ち、最上位の状態が数十に膨らむ。

### 3. 上から下へ

- 最上位は各部品に、描くのに必要な分だけの読み取り専用の表示用データを渡す。
- 部品は受け取った表示用データをそのまま描く。アプリの状態から判断を導かない。

反例: 部品がアプリの状態全体への参照を受け取り、「この項目は編集できるか」を自分で判定して
ボタンの有効・無効を決める。

### 4. 下から上へ

- 部品は利用者の操作をイベントで最上位に知らせるだけで、ほかの部品やアプリの状態を直接変えない。
- イベントの仲介をするのは最上位だけ。
- キーボード操作は、フレームワークが子から親へ伝える仕組みを持つならそれを使い、自前の仕組みを
  重ねない。

反例: 一覧の部品が、行を選んだときに詳細の部品の状態を直接書き換える。
フレームワークのキー入力の伝播と別に、自前のキー配送表を最上位に作る。

### 5. ダイアログ

- 同時に開けるダイアログは 1 つ。どれが開いているかを最上位が 1 つの状態として持つ。
- 利用者の操作で開くものも、アプリの状態が求めるもの(エラー、確認など)も、同じ層に出す。
- 競合したときの優先順位は 1 か所に書く。

反例: ダイアログごとに「開いているか」の真偽値を持ち、エラーと確認が同時に開く。
エラーダイアログだけ別の仕組みで出す。

### 6. 描き直しの単位

- 描き直しの単位は部品。自分の表示用データが変わった部品と、自分で描き直しを求めた部品だけを
  描き直す。
- 最上位は、前と同じ表示用データを部品に渡し直さない。

反例: 1 つの状態が変わるたびに、最上位が全部品へ新しく作った表示用データを渡し、
ウィンドウ全体が描き直される。

### 7. 描画は読むだけ

- 描画の処理の中で状態を書き換えない。グローバルな設定(テーマ、フォント、スタイルなど)も含む。

反例: 描画の中で「初回だけ」の初期化フラグを立てる。描画の途中でグローバルなスタイルを
書き換え、戻し忘れる。

### 8. フォーカス

- 領域をまたぐフォーカスの移動は最上位が決める。
- 部品は自分の中のフォーカス移動だけを行う。

反例: 一覧の部品が、末尾で下キーを押されたときに詳細の部品の入力欄へフォーカスを移す。

### 9. 守らせ方

- 機械で調べられる規則は、型・可視性・品質ゲートで守らせる。例: アプリの状態を扱える
  モジュールを最上位に限る、部品の状態を非公開にする、最上位の型の振る舞いを最上位の
  モジュールの外で足さない。
- 機械で調べられない規則はレビューで確かめる。

反例: 「部品からアプリの状態を触らない」をコメントの約束だけで守らせ、アプリの状態が
どのモジュールからも書き換えられる可視性のままにする。

### 10. テスト

- 部品は、表示用データを渡して作り、表示と、操作で出るイベントを部品ごとに確かめる。
- 最上位を通した結合テストも持つ。

反例: 部品のテストのたびにアプリ全体を起動する。部品のテストだけで、最上位の仲介を
通したテストがない。

## 判断と例外

- 1 つのダイアログの中で確認が要る場合(設定ダイアログの中の破棄確認など)も、
  ダイアログを重ねず、「どれが開いているか」の状態の値を 1 つ増やして表す。
  規範 5 の核は「1 つの状態で表し、優先順位を 1 か所に書く」ことにある。
- フレームワークが毎フレーム全体を描く方式で、描き直しの単位をアプリ側で選べない場合、
  規範 6 の当てはめ(変わっていない部品の表示用データを作り直さない、など)は
  プロジェクトの文書に書く。
- 部品の中に、表示用データの整形(日付の表記、桁区切りなど)を置くことは妨げない。
  禁じるのは、アプリの状態から判断(可否、状態による分岐)を導くこと。

合格条件: SKILL.md の判断基準の節が、上の 3 点を述べている。

## 既存スキルとの境界

- ba0918-design: 層の向き、純粋なドメイン、依存注入、不変、型による検証の一般則を持つ。
  この規約はそれらを再掲せず、GUI での現れ方(アプリの状態はドメイン層が持つ、描画は読むだけ、
  可視性で守らせる)だけを書き、一般則は名前で参照する。
- ba0918-testing / ba0918-tdd: テストの一般則と手順。この規約は、部品と最上位を
  それぞれ何でテストするかだけを書く。
- ba0918-verification: レビューの進め方。この規約は、レビューで突き合わせる規則を与えるだけ。

- `skills/ba0918-gui-structure/SKILL.md` を追加する

- CHANGELOG の Unreleased に追加の記載

## 作らないもの

- 特定のフレームワーク名・プロジェクト名、フレームワークごとの当てはめ
- 領域の一覧やダイアログの優先順位といった、アプリごとの具体値
- 見た目・アクセシビリティの規則
- ba0918-design の一般則の再掲

## 却下

- スキル本文に GUI 設計の型の名前を出す — その型の一般的な解釈が持ち込まれ、意図とずれる
- `ba0918-gui` という名前 — GUI の規則すべてを扱うように読める。見た目やアクセシビリティは
  この規約の対象外で、扱うなら領域が違うので別スキルになる。そのとき名前が紛らわしく、
  公開後の改名は各プロジェクトの AGENTS.md の行を壊す
- `ba0918-ui` という名前 — ターミナルの画面まで対象を広げることになる。この規約は GUI に限る
- `always` のルーティング — GUI を持たないプロジェクトにまで毎回読ませる
- ルーティングなし(description だけの発火) — scaffold が生成するルーティング表に行が出ず、
  プロジェクトの AGENTS.md から名指しできない
- 記事の型をそのまま採用する — 型ごとに症状に効くかを見て、効く部分だけを規則にした
