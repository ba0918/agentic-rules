# 置換可能性の規約(ba0918-design / ba0918-reuse 追記)

## 目的と出典

AI による高速なコード生成は、動くが取り壊せない構造 — 実装の詳細が保存データや利用者に
固定され、あとから差し替えられないコード — を無批判に蓄積しやすい。出典は記事
The Velocity Trap (Atomic Object,
https://spin.atomicobject.com/velocity-trap-best-architects-slow/) の Six-Month Test
(「6ヶ月後に取り壊すのはどれほど痛いか」を生成前に自問する)。

ただし時間の比喩は検証不能なので採らない。採るのは検証可能な言い換えだけである:
**実装の変更と契約の変更を分離し、その影響をテストで観測できること**。
これは保守性という第二の原則ではなく、テスタビリティ(ba0918-design の唯一の柱)の
一側面として扱う。

## 判定基準

固定(保存形式・公開 API などが事実上変更困難になること)自体は違反ではない。
判定は「意図していたか」では行わない — 意図は後付けで正当化できるためである。
観測可能な 2 点で判定する:

- 何を契約として**宣言**したか(公開 API・保存形式が契約として明示され、
  契約テストで固定されているか)
- 変更経路が**検証可能**か(互換読み取り・移行・明示的拒否のいずれかの経路を
  テストで通せるか)

宣言された契約に由来する固定は正当である。違反は、意図していない実装の詳細が
保存データや利用者へ漏れて不可逆に固定され、変更経路も検証できない状態を指す。

## ba0918-design への追記

Rules に加える規範:

- 依存先や保存方式に固有の表現は、宣言した境界の内側に留める
- 永続形式を変更するときは、採用した移行・互換・明示的拒否の経路をテストする
- 将来の置換だけを理由に抽象を追加しない(投機的抽象の禁止 — 抑制方向の安全弁)

Judgment に加える判断基準: 実装を差し替えたときに呼び出し側・ドメインルール・
そのテストまで書き換わるなら、テストが契約ではなく実装の詳細を固定している。
直すのはテストと境界であり、置換を安くするための抽象追加ではない。

Evidence は関係する差分だけに要求する:

- 境界を変更した差分: 今回変更した公開面に、依存・保存方式固有の表現が
  **新たに**露出していないこと。差分によるリポジトリ全体の不在証明は要求しない —
  差分は不在を証明できず、要求すれば形骸化した儀式になる
- 永続形式を変更した差分: 旧形式の代表例が、採用した変更経路を通るテスト結果

## ba0918-reuse への追記

層ごとの採用/自作の記録に、条件付きの 1 項目を加える: 新しい外部依存が永続形式
または公開契約を固定する場合に限り、固定される対象を採用記録に含める。
該当しない依存に定型行(fixation: none など)を書かせる義務は設けない —
無条件の記録義務は定型句化し、レビューを形骸化させる。

自作物(自前スキーマ・イベント名・ID 体系など)の固定化は reuse の記録対象ではなく、
ba0918-design の境界局所化の規範が構造として扱う。reuse の「記録を裁き、判決は
裁かない」という原則はそのまま維持する。

## 適用範囲

既存コードの固定化の棚卸しは要求しない。対象は、新たな変更(差分)が新しい漏洩や
移行不能を作らないことのみである。これは抑制優先のトレードオフとして受け入れる。
運用して違和感が出た時点で見直す。
