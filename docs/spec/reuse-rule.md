# 再利用判断の規約(ba0918-reuse)

## 目的

AI コーディングエージェントには、人間が名前を挙げた部分では既存のライブラリを使い、
誰も言及しなかった部分では既存の解を探しもせずに自前実装する、という偏りがある。
実例として、SSH 経由で SVN サーバを管理する社内ツールの開発で、人間が提案した
Web フレームワーク(Slim)は採用された一方、誰も言及しなかったプロセス管理層は、
定番ライブラリ(symfony/process)が存在するのに低レベル API で自前実装された。

この規約は、その偏りを「実装方式を決める前に、既存の解を探索し判断の記録を残すこと」を
義務づけることで塞ぐ。「車輪の再発明をするな」という禁止は、適切な既存解が存在しなかった
ことを証明できない以上検証不能なので採らない。裁くのは記録の有無だけであり、
採用・自作どちらの結論も、理由が記録されていれば正当と扱う。

## 発火条件

設計段階 — 何かを新しく作る、または作り替える実装方式を決める前 — に読む。
ルーティングのメタデータは `ba0918-routing: required:design` を宣言し、
生成される AGENTS.md のルーティング表に design 工程の行として現れる。
常時適用(always)にはしない。層分解という重い手順をすべての作業に課さないためである。

## 規範の骨子

### 1. 層への分解

実装方式を決める前に、タスクを層に分解して列挙する。層とは
「独立して採用/自作の判断ができる単位」を指す。たとえば前述のツールは
Web 外枠・SSH 輸送・プロセス管理・Result 型ユーティリティの 4 層に分かれる。
それぞれに別の代替品が存在するからである。
ツール全体を 1 層と数える運用は、この基準への違反として扱う。
層の列挙自体が観測可能な成果物であり、列挙が存在しないことは
「探索していない」ことの機械的な判定材料になる。

### 2. 層ごとの探索順序(拡張版 Ladder)

各層について、次の順で既存の解を確認し、最初に成立した段で止まる。

1. その層はそもそも必要か(なくても目的が達成できないか)
2. このコードベースに既にないか
3. 言語の標準ライブラリにないか
4. プラットフォームの組み込み機能にないか
5. 導入済みの依存パッケージにないか
6. エコシステムの定番(パッケージレジストリ上でそのドメインの定番として
   知られているもの)にないか
7. 数行で書けてしまわないか
8. 最小限の自作

この順序は公開スキル ponytail の The Ladder を下敷きにするが、
第 6 段(未導入のエコシステム定番)は独自の挿入である。原典の梯子は
「導入済み依存」までしか見ないため、定番が未導入という一番ありがちな状況で
自作に落ちてしまう。この規約が防ぎたい失敗はまさにそこにある。

### 3. 記録

層ごとに、採用したか自作したかの別と、その理由を 1 行残す。
「依存を増やしたくないので自作」も、記録されていれば正当な判断である。
人間がその技術を提案したことは記録の免除理由にならない — 提案された層も
されなかった層も同じ形式で残す。

記録の置き場所はプロジェクトごとの契約に委ねるが、粒度で使い分ける:
短い理由はコード中の Why-not コメント(なぜ自明な代替案を採らなかったか)、
候補比較を伴う長い理由はコミットログの Why 側に置く。
これは情報配置の規約(ba0918-placement)の四象限に従った配置である。

### 4. タイムボックスと浮上

探索には時間の上限を設ける(値はプロジェクト側で決める)。ニッチな領域では
探索しても既製品が無いことが多く、無制限の探索義務は費用対効果が崩壊するため。
時間上限に達した場合は、その事実をその層の自作理由として記録する。
また、依存の制限方針などの制約が大規模な自前実装を強制する場合、エージェントは
黙って従わず、その帰結(実装・保守・セキュリティレビューをすべて自前で負うこと)を
実装前に人間へ提示する。

## 既存スキルとの境界

- ba0918-design は「どう作るか」(内部品質)の規約。本規約は「そもそも作るか、
  既存を使うか」というその手前の意思決定を扱う。内容の重複ではなく時系列の前後関係
- ba0918-placement は記録が最終的に落ちる場所(コメント/コミットログ)の規約。
  本規約は何を記録するかの形状だけを定め、配置は placement に従う

## 検出と強制

記録の有無の検出は既存のレビュー工程(人間、または review 工程で発火する検証規範)に
乗せる。lint や CI のような新しい強制機構は作らない — このリポジトリはドメインルール
だけを持ち、ワークフロー自動化を持たないという役割分担に従う。

## 命名と配置

スキル名は `ba0918-reuse`。命名規約 `ba0918-<ドメイン名詞>` に従う。
「初期スキル」の延期原則(必要が実際に発生した時点で追加する)は、
上記ツールの実害によって発火したものとして消費する。
