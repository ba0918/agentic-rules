# 継ぎ目の規約(ba0918-design 追記)

## 目的と出典

AI による高速なコード生成は、規模に釣り合わない構造を無批判に蓄積しやすい —
実装が 1 つしかない interface、呼び出し側が 1 つしかない注入点、変種が 1 つしかない
registry、切り替える者のいない設定スイッチ。ba0918-design の Rules は「依存を注入せよ」
「変種は module 追加で」と**形**を命じるが、その形を**いつ入れるか**の門が無い。
無条件の Rules は散文の Judgment(投機的抽象の禁止)に勝つため、抑制側の規範が Rules に
無いままだと、設計規範そのものが過剰設計を生む。

原型は YAGNI(You Aren't Gonna Need It)の精神である。ただし「要らなかった」は証明
できないので、精神のままでは検証不能で、レビューで裁けない。採るのは検証可能な
言い換えだけである: **継ぎ目(seam — interface・注入点・registry・設定スイッチ)は、
同じ変更の中にそれを必要とするテストか 2 つ目の実装があるときに限って入れる**。

これは簡潔さという第二の原則ではなく、テスタビリティ(ba0918-design の唯一の柱)の
一側面として扱う。使い手のいない継ぎ目は、どのテストも通らない経路を増やす —
テストされない結合面を設計に持ち込むことになる。

## 判定基準

「将来必要になる」「拡張性のため」は意図であり、判定には使わない — 意図は後付けで
正当化できるためである。観測可能な 2 点で判定する:

- 継ぎ目の裏に**2 つ目の実装**が同じ変更に存在するか
- 継ぎ目が無ければ書けない**テスト**が同じ変更に存在するか
  (例: clock を引数にしなければ、期限切れを任意の時刻で検証できない)

どちらも無い継ぎ目は違反。どちらかがあれば正当である。行数・ファイル数といった
「規模」では裁かない — 小さくても使い手のある継ぎ目は正当で、大きくても使い手の
無い継ぎ目は違反である。

## 既存規範との関係

Rules にある「将来の置換だけを理由に抽象を追加しない」は残す。あれは置換可能性の
文脈での特殊形であり、本規約はその一般形として別行で加える。既存行を吸収・改稿
すると既存ルールの意味変更(BREAKING)に触れるため、追加のみとする。

「外部依存はすべて注入せよ」との衝突は無い。clock を注入する変更は、その瞬間を
固定する分離テストを同じ変更に持つから正当である。本規約が禁じるのは注入ではなく、
それを必要とするテストの無い継ぎ目である。

ba0918-reuse の ladder 1 段目(「その層はそもそも要るか」)と役割が重なるように
見えるが、reuse は**依存の採用/自作**を、本規約は**作るものの構造**を扱う。
reuse の Scope が構造を ba0918-design の管轄と明記しているため、置き場所は design である。

## ba0918-design への追記

Rules に加える規範(1 行):

- interface・注入点・registry・設定スイッチは、同じ変更にそれを必要とするテストか
  2 つ目の実装が無い限り導入しない。無ければ具体物を直接呼ぶ

Judgment に加える判断基準: 継ぎ目を正当化するのは現在の使い手であり、予測された
使い手ではない。レビューは差分の中で使い手を数える。継ぎ目の裏に実装が 1 つ、
それを要求するテストが 0 なら、その継ぎ目は削って具体物を直接呼ぶ。2 つ目の実装が
来たとき、継ぎ目はその変更の中で、その実装と一緒に入る。

Examples に加える対比: 実装 1 つの interface + factory + 設定キー(Bad)と、
具体物の直接呼び出し(Good)。

Evidence に加える項目(関係する差分だけに要求する): 変更が導入した継ぎ目ごとに、
同じ差分の中でそれを使うテストまたは 2 つ目の実装。差分によるリポジトリ全体の
証明は要求しない。

## 適用範囲

既存コードの継ぎ目の棚卸しは要求しない。対象は、新たな変更(差分)が使い手の無い
継ぎ目を新しく作らないことのみである。description は変更しない — 発火条件は
変わらず、変わるのは読まれた後の規範だけである。運用して違和感が出た時点で見直す。
