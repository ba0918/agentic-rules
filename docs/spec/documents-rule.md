# 文書の配置と寿命の規約(ba0918-documents)

## 目的

エージェントに仕事を任せると、エージェントは調べたことや決めたことを文書ファイルとして残す。
置き場所の決まりがないと、エージェントはそのたびに新しいディレクトリを作って文書を置き、
リポジトリの文書が散らばる。運用の中でこれが問題になった。散らばりは次の形で現れる。

- 同じ種類の文書が、セッションごとに違うディレクトリに置かれる
- 同じ話題の文書が、既存の文書を探さずに 2 つ目、3 つ目と作られる
- 役目を終えたメモや計画が消されずに残る
- どこに何があるかを示す入口がなく、人もエージェントも全体を把握できない

散らばりより重い害は、古くなった文書である。文書は、コードと違って何にも検査されない。
実態と食い違った文書が残っていると、後から来たエージェントはそれを今の事実として読み、
誤った前提で作業する(ハルシネーションの入口になる)。間違った情報は、情報がないことより悪い。

この規約は、文書の「種類と置き場所・作ってよい条件と粒度・寿命と剪定・書式・導線」を定める。
中心は寿命と剪定であり、置き場所の統一はそれを点検できるようにするための前提である。

## 発火条件

ルーティングのメタデータは `ba0918-routing: required:document` を宣言する。
生成される AGENTS.md のルーティング表に `document` の行として現れる。

発火させる場面:

- 文書ファイルを作る、または作るかどうかを決める
- 文書を移す・改名する・消す、文書のディレクトリを整理する
- 文書の棚卸し(古い文書・不要な文書の洗い出し)をする

`always` にはしない。文書を作らない作業にまで、ツリーの規則を読ませる理由がないため。
ただし、文書が古くなるのは文書を書くときではなく、コードを変えるときである。この時点で
読まれるよう、「変更で偽になった文書はその変更の中で直すか消す」と「過去の記録を今の事実として
読まない」の 2 点だけは、常時読まれる ba0918-placement にも書く(下の「既存スキルとの境界」)。

## 対象

人やエージェントが手で書き、リポジトリで追跡する文書ファイル。

扱わないもの:

- ルート直下の慣習的なファイル(README、CHANGELOG、LICENSE、CONTRIBUTING、AGENTS.md、
  PROJECT.md など)の置き場所。慣習のとおりルートに置く。中身の規則はそれぞれの担当スキルにある
- パッケージやモジュールの直下に置く README
- コードから生成される文書(API リファレンスの自動生成など)
- スキルのファイル(ba0918-skill-authoring の担当)
- 文章の分かりやすさ(ba0918-readability の担当)
- コメント・テスト名・コミットメッセージに何を書くか(ba0918-placement の担当)
- 文書に秘密や実行環境の情報を書かないこと(ba0918-secrets の担当)

## 規範

各節の合格条件は、SKILL.md の必須ルールの節がその規範を述べていることを指す。

### 1. 種類と置き場所

既定のツリー:

```
docs/
  README.md        入口。各ディレクトリの役割と、いま正となる文書への索引
  spec/            仕様。システムが何をすべきか
  architecture/    今の構造。全体像、データモデル、API など
  decision/
    adr/           確定した決定。1 決定 1 ファイル
    records/       検討・壁打ちの記録。1 回の検討 1 ファイル
  plans/           実装計画。1 計画 1 ファイル
  guides/          人が手順として読む使い方
  notes/           共有する価値があり、まだ他の種類に収まっていない調査結果
.agents/           セッション内の作業メモ。ignore 済みで、コミットしない
```

- 文書は、上の種類のどれか 1 つに属させる。
- どれにも当てはまらないときは、エージェントの判断で新しいディレクトリを作らない。
  人に確かめる。確かめられないときは notes/ に置き、そうしたことを報告する。
- 新しい種類のディレクトリを足すのはプロジェクトの決定である。足したら入口(docs/README.md)に
  役割を書く。
- プロジェクトの文書(PROJECT.md など)や、文書を検査・生成するツールの設定が別の置き場所を
  宣言していれば、そちらに従う。宣言された置き場所にも、この規約の寿命・書式・導線の規範は当てはまる。
- ディレクトリは、その種類の最初の文書を置くときに作る。空のディレクトリを先回りして並べない。
- 種類の下の階層は、話題やモジュールで 1 段までにする。

既定の名前の理由:

- `spec/`: 一般的な語で、特定のツールを使わないプロジェクトでも意味が通る。仕様を検査する
  ツールが別の名前(例: `ir/`)を設定で宣言していれば、宣言が勝つ
- `decision/adr/`・`decision/records/`・`plans/`: 仕様を検査するツールの既定と同じにして、
  ツールを使うプロジェクトでも使わないプロジェクトでも同じ形にする
- `architecture/`: 仕様(何をすべきか)と構造(今どう組まれているか)は更新の契機が違うので、
  種類を分ける。テーブル構成や API 仕様もここに入れ、別の種類にはしない
- ルート直下の `ARCHITECTURE.md` を既定にしない。構造の文書の置き場所が 2 つに割れるため

合格条件: 上の 6 点と既定のツリーが述べられている。
反例: エージェントが `docs/investigation/` や `docs/memo-2026-10/` を自分の判断で作る。
反例: 構造の文書を `notes/architecture.md` に置く(notes は寿命つきの種類で、構造の文書は現在形で
更新し続ける種類のため)。

### 2. 作ってよい条件と粒度

- 新しい文書を作る前に、同じ話題の既存の文書を探す。あれば追記するか書き直す。
  同じ話題の文書を 2 つ作らない。
- 1 つの文書は 1 つの話題を扱う。ADR は 1 つの決定、plan は 1 つのブランチ分の作業、
  record は 1 回の検討。
- 会話の中で役目を終える内容(作業途中の箇条書き、試行のログ、会話の要約)は文書にしない。
  セッションの中で要るなら `.agents/` に置く。
- コード・テスト・コミットメッセージ・コメントで表せる内容は文書にしない(ba0918-placement の四象限が先)。
- 別の文書やコードにある内容を写さない。リンクで指す。写しは片方だけが直されてずれ、
  古い情報の発生源になる。機械可読な正本(スキーマ定義、マイグレーション、API 定義ファイルなど)が
  あれば、それが正である。文書は全体像と理由を書き、正本へリンクする。

合格条件: 上の 5 点が述べられている。
反例: API 定義ファイルの各エンドポイントを、`architecture/api.md` に表として書き写す。

### 3. 寿命と剪定

種類ごとに寿命を決める。

| 寿命 | 種類 | 扱い |
|---|---|---|
| 現在形 | spec、architecture、guides、入口 | 常に今の事実を書く。実態が変わったら書き換える。変更履歴の節を持たない(履歴は版管理にある) |
| 記録 | adr、records | 書いた時点の記録。中身を書き換えない。後の決定で覆ったら、覆った側への参照と状態だけを書き足す |
| 期限つき | plans、notes | plan は、そのブランチがマージまたは放棄されたら消す。note は、他の種類に昇格させるか、役目を終えたら消す |

剪定の規範:

- 変更で偽になった文書は、その変更の中で直すか消す。後回しにしない。
  変更の前に、変更する振る舞い・名前・構造に触れている文書を探す。
- 消した文書を退避用のディレクトリ(`archive/`、`old/`、`deprecated/` など)に移さない。
  版管理の履歴が退避先である。退避用のディレクトリに置いた文書も、エージェントは探索で拾ってしまう。
- 新しい決定を記録するときは、同じ決定や仕組みを扱う古い記録を探し、覆したものには
  覆した側への参照と状態をその変更の中で書き足す。覆された記録が「有効な決定」に見えたまま残ることを防ぐ。
- 記録の種類(adr、records)は、今の事実の根拠として読まない。今の事実は、コード・テスト・
  現在形の文書にある。記録と現在形の文書が食い違えば、現在形の文書が正である。
- 読んでいる文書と実態の食い違いに気づいたら、その文書に頼らない。今の作業の範囲で直せるなら
  直す。範囲外なら、どの文書のどこが何と食い違うかを報告する。黙って放置しない。
- 期限つきの文書は、すべてが進行中の作業に対応している状態を保つ。棚卸しでは、対応する作業が
  ない plan と note を洗い出し、消すか、持ち主に確かめる。

合格条件: 寿命の表と上の 6 点が述べられ、「変更で偽になった文書はその変更の中で直すか消す」と
「記録を今の事実の根拠として読まない」が SKILL.md 本体にある。
反例: 実装し終えた plan を `docs/plans/done/` に移して残す。
反例: 設計を変える変更で、古い設計を説明する architecture の文書をそのままにし、
「文書の更新は別の作業」と報告する。

### 4. 書式

- 書式を持つツールが扱う種類は、ツールの書式に従う。この規約は書式を重ねて定めない。
- それ以外の文書は、最初の行を見出しの題名にし、その直後に「この文書は何か」を 1〜2 文で書く。
- ファイル名は小文字とハイフンで、話題を表す。日付に意味がある種類(records など)だけ、
  先頭に `YYYY-MM-DD-` を付ける。連番の種類(adr)は番号を先頭に付ける。
- 文書の言語はプロジェクトの決まりに従う。
- 現在形の文書に「最終更新日」や「以前は〜だった」を書かない。古さの判断材料にならないうえ、
  過去の状態を今の事実と並べることになる。
- 現在形の文書に、実装の状況の注記(「実装済み」「未実装」「将来対応」など)を書かない。
  状況は変わるのに注記は直されず、真っ先に古くなる。状況はコードと計画が持つ。

合格条件: 上の 6 点が述べられている。

### 5. 導線

- docs/README.md を入口にする。各ディレクトリの役割と、いま正となる主な文書を載せる。
- ディレクトリを足したり、入口に載る文書を足したり消したりしたら、同じ変更で入口も直す。
- 文書どうしは相対リンクでつなぐ(ADR から元の検討の記録へ、plan から仕様へ、など)。
- エージェントが常時読むプロジェクト文脈(PROJECT.md など)から、入口へ 1 行で辿れるようにする。

合格条件: 上の 4 点が述べられている。

## 判断と例外

- 文書の少ないプロジェクトに、ツリー全体を作らせない。種類のディレクトリは、その種類の最初の
  文書ができたときに作る。
- 剪定は消すことが目的ではなく、残っている文書を正しく保つことが目的である。正しく、今も読まれる
  文書を、古いという理由だけで消さない。
- 消すことは版管理の上では取り消せるが、他人が書いた文書を範囲外で消すと持ち主の作業を壊しうる。
  今の作業の範囲外にある古い文書は、消さずに報告する。棚卸しを頼まれたときは、その棚卸しが範囲である。

合格条件: SKILL.md の判断基準の節が、上の 3 点を述べている。

## 完了時の証拠

- 作った・移した文書のパスが、既定のツリーか宣言された置き場所の内側にあること(`git status` の出力)
- 新しい文書を作る前に既存の文書を探したこと(検索のコマンドとその結果)
- 振る舞い・名前・構造を変えた変更では、それに触れる文書の検索結果と、直した・消した文書の差分
  (該当なしならその検索結果)
- ディレクトリを足したときは、入口の差分

合格条件: SKILL.md の証拠の節が上の 4 点を求めている。

## 既存スキルとの境界

- ba0918-placement: 1 つの変更に付く文章(コメント・テスト名・コミットメッセージ)の置き場所。
  文書ファイルは扱わない。Scope に、独立した文書ファイルはこのスキルの担当だと 1 行足す。
  また、剪定のうち作業の種類を問わず要る 2 点(変更で偽になった文書はその変更の中で直すか消す、
  記録を今の事実の根拠として読まない)を、placement の規則にも書く。スキル間の重複は許す
  (`skill-authoring-rule.md` 規範 4)。
- ba0918-readability: 文書の文章の分かりやすさ。この規約は、どこに・何を・いつ作り、いつ消すかだけを扱う。
- ba0918-secrets: 文書に秘密や実行環境の情報を書かないこと。
- ba0918-worktree: `.agents/` の下の worktree の置き場所。この規約は `.agents/` をセッション内の
  作業メモの置き場所としても使うが、ignore の範囲の決め方は worktree の規範に従う。

統合しなかった理由: `skill-authoring-rule.md` 規範 1 の基準(領域が違う、または読まれる作業の
種類が違う部分は別スキルに分ける)を当てた。

- placement に節として入れない。placement の対象は 1 つの変更に付く文章で、文書ファイルの作成・
  配置・寿命は読まれる作業が違う。placement は `always` なので、統合すると全セッションが
  文書ツリーの規則を読むことになる。
- placement の `references/` にも入れない。`references/` は同じ領域の特定の状況のためのもので、
  文書ツリーの扱いは別の作業である。
- readability に入れない。文章の分かりやすさと、文書の置き場所・寿命は別の領域である。

## リポジトリへの組み込み

- `skills/ba0918-documents/SKILL.md` を追加する
- `skills/ba0918-placement/SKILL.md` の Scope に境界の 1 行、Rules に剪定の 2 行を足す
- README と README-ja のスキル表に 1 行(Loaded by 列は `required:document`)
- CHANGELOG の Unreleased に追加の記載
- `repository-design.md` の「初期スキル」表に 1 行
- `.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の description に、
  同じ文字列で文書の配置と寿命を足す。plugin.json の keywords に `documents` を足す
- このリポジトリの AGENTS.md のルーティング表に `document` の行を足す

このリポジトリ自身の文書(`docs/spec/` のみ)に入口の docs/README.md を足すことは、この仕様の範囲に入れない。

## 受け入れ確認

- 人による確認: SKILL.md を、この仕様の各節の合格条件と 1 つずつ突き合わせる
- 既存チェッカー: `python3 scripts/validate.py` と pytest、CI の skills-ref が通る

この規約を機械検査するルールはバリデータに足さない。

## 作らないもの

- 特定のツールの名前や設定方法
- 文書の中身のテンプレート(ADR の節立てなど)。ツールかプロジェクトが持つ
- 文書の古さを日数などの数値で判定する基準。適切な値がプロジェクトで変わり、古さは日数ではなく
  実態との食い違いで決まる

## 却下

- 既存スキル(placement / readability)への統合 — 上の「統合しなかった理由」
- 仕様のディレクトリの既定を `ir/` にする — 特定のツールの用語で、使わないプロジェクトには意味が通らない
- ルート直下の `ARCHITECTURE.md` を既定にする — 構造の文書の置き場所が割れる
- 構造の文書を notes/ に置く — notes は寿命つきの種類である
- 完了した plan を状態を書いて残す — 進行中かどうかを毎回判定することになり、古い計画を今の方針として読む誤りの元になる
- notes/ を置かない — 行き場のない調査結果が、また新しいディレクトリを生む
- 退避用のディレクトリ — 探索で拾われ、古い情報を今の事実として読む誤りの元になる
- `always` のルーティング — 「発火条件」の節
