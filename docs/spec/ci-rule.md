# CI ワークフローの規約(ba0918-ci)

## 目的

CI のワークフロー定義(GitHub Actions のワークフローファイルなど)は、エージェントに
自由に書かせると、プロダクトごとに品質が揃わず、書くたびに作り方が変わる。運用の中で、
この不揃いが問題になった。CI の定義は次の 2 つの点で、他のコードより不揃いの害が大きい。

- CI は秘密情報と書き込み権限を持って、外部のコードを実行する。外部の action をタグで
  参照すれば、タグの付け替え 1 つで秘密情報が抜かれる(2025 年の tj-actions/changed-files の
  事件がこの形だった)。フォークからの PR のコードを秘密情報のある文脈で動かせば、
  誰でもリポジトリに書き込める。権限を書かなければ、何が渡っているかを誰も読めない。
- CI の定義はローカルで実行して確かめにくく、書いた人以外が読み解きにくい。プロダクトごとに
  形が違えば、移るたびに読み直しになる。

これらには広く合意された作法がある。GitHub 自身も 2025 年から既定値と強制ポリシーを
締め始めている(組織ポリシーによる SHA 固定の強制、`pull_request_target` のワークフロー定義を
既定ブランチに固定する変更)。この規約は、その作法のうち CI 基盤に依らない部分を規範として
定め、GitHub Actions での具体的な書き方を `references/` に分ける。

## 発火条件

ルーティングのメタデータは `ba0918-routing: required:ci` を宣言する。
生成される AGENTS.md のルーティング表に `ci` の行として現れ、CI の定義を書く・変える作業の
ときに読まれる。

発火させる場面:

- ワークフローファイルや CI の設定を新しく書く、または変更する
- ジョブ・ステップ・外部の action を足す
- プロジェクトに CI を用意する
- 既存の CI 定義をレビュー・監査する

`always` にはしない。CI に触れない作業にまで読ませる理由がないため。
ルーティングなし(description による発火だけ)にもしない。エージェントは別の作業の
ついでに CI を足したり直したりすることが多く、そのとき「CI の作業をしている」と自覚しない
まま進むと description の発火だけでは読まれない。AGENTS.md の表に行を出して名指しする。

## 対象

CI/CD のパイプライン定義すべて。リポジトリに置かれ、プッシュ・PR・タグ・手動起動・定期実行などを
契機に、ホストされた実行環境でジョブを走らせる設定ファイルを指す。

規範は CI 基盤に依らない言葉で書き、基盤ごとの具体的な書き方は `references/` に置く。
最初に用意するのは GitHub Actions 向けの `references/github-actions.md` で、他の基盤が
要るようになったら同じ形でファイルを足す(`skill-authoring-rule.md` 規範 2・3・4)。

扱わないもの: 実行環境(ランナー)そのものの構築と管理、組織単位のポリシー設定、
デプロイ戦略の設計、ビルドシステムやテストの中身、プロジェクトの依存関係の管理
(依存のマニフェストとロックファイルで管理されるもの)。

## 規範

各節の合格条件は、SKILL.md の必須ルールの節がその規範を述べていることを指す。

### 1. 既存の形に揃える

- 新しいワークフローを書く前に、リポジトリの既存のワークフローを読み、その構成・命名・
  書き方に揃える。
- 既存のワークフローがこの規約に反しているときは、規約の側に揃える。反している箇所を
  横に写して増やさない。

この節が今回の問題(作り方が毎回変わる)に直接答える。規約が決めない細部(ファイル名、
ジョブの分け方など)は、そのリポジトリの既存の形が基準になる。

合格条件: 上の 2 点が述べられている。
反例: 既存のワークフローと無関係な形で新しいワークフローを書く。
反例: 既存のワークフローのタグ参照を、新しいワークフローにもそのまま写す。

### 2. 外部のコードを固定する

- パイプラインが取り込んで実行する外部のもの(action、他リポジトリの再利用ワークフロー、
  コンテナイメージ、スクリプトで取ってくるツール)は、書き換えられない参照で指す。
  完全なコミットハッシュ、イメージのダイジェスト、版とチェックサムである。
  タグやブランチ名では指さない。
- 固定した参照の横に、人が読める版をコメントで残す。
- 推移的な依存(固定した action が中で使うもの)も固定の対象である。基盤がロックの仕組みを
  提供していて、プロジェクトがそれを採用しているときは、ロックファイルを正とし、
  その生成ツールで更新する。手で書き換えない。
- 固定した参照の更新は、自動の依存更新ツールを基盤向けに設定して行う。
  固定をやめて「常に最新」に戻すことで更新しない。

合格条件: 上の 4 点が述べられている。
反例: `uses: some/action@v3`。
反例: ロックファイルのハッシュを手で書き換える。

ロックの仕組みについて: GitHub は `.github/workflows/actions.lock` 形式とその生成ツールを
公開しているが、どちらも pre-1.0 のプレビューで、形式もコマンドも予告なく変わると明記している。
変わると分かっている詳細を書けば、古くなって誤りの入口になる。そのため SKILL.md の本文には
原則(ロックを採用したならそれを正とする)だけを書き、`references/github-actions.md` には
「プレビューであり、採用はプロジェクトの判断」とだけ書いて、コマンドやフラグは書かない。
1.0 になったら references を見直す。

### 3. 権限を最小にし、明示する

- パイプラインに渡るトークンの権限は、ワークフローの先頭で明示し、既定を読み取りのみ
  (または権限なし)にする。書き込みが要るジョブだけで広げる。
- 権限を広げた箇所には、なぜ要るかをコメントで書く。
- クラウドなど外部サービスへの認証は、提供されていれば短命な連携認証(OIDC)を使い、
  長期の鍵を保管しない。
- 秘密情報は、それを使うステップにだけ渡す。ワークフロー全体やジョブ全体には渡さない。
- デプロイの認証情報は、保護ルール(承認者、対象ブランチの制限)を持つ環境の背後に置く。
- 取得したリポジトリにトークンを残さない。push しないジョブでは、チェックアウトの
  認証情報を後続のステップに残さない設定にする。

合格条件: 上の 6 点が述べられている。
反例: 権限を書かず、リポジトリの既定に任せる。
反例: 秘密情報をワークフロー全体の環境変数に置く。

### 4. 信頼できない入力を実行しない

- 信頼できない投稿者のコード(フォークからの PR など)を、秘密情報か書き込み権限を持つ
  文脈で実行しない。
- イベントの内容(PR のタイトルや本文、ブランチ名、コミットメッセージ、手動起動の入力)を
  スクリプトの本文に埋め込まない。環境変数として渡し、シェルでは引用して使う。
- リリース・公開・デプロイを行うジョブでは、キャッシュを復元しない。
- 信頼できない PR のジョブを、使い回しの実行環境(自前の永続ランナーなど)で走らせない。

合格条件: 上の 4 点が述べられ、SKILL.md 本体に置かれている(安全に関わる即応部分なので
`references/` へ移さない。基盤ごとの具体形だけを references に置く)。
反例: `pull_request_target` の契機で PR の head を checkout してテストを走らせる。
反例: `run: echo "${{ github.event.pull_request.title }}"`。

### 5. 走り方を有限で予測できるものにする

- すべてのジョブに実行時間の上限を置く。
- 同じブランチや PR の古い実行は、新しい実行が始まったら取り消す。デプロイは直列にし、
  途中で取り消さない。
- キャッシュのキーは、依存のロックファイルの内容から導く。
- シェルは最初の失敗で止まる設定で動かす。パイプの途中の失敗も含める。
- 実行環境のイメージと言語ランタイムの版は意図して選ぶ。「最新」を指す名前を使うなら、
  それが変わることを受け入れたうえで使う。

合格条件: 上の 5 点が述べられている。
反例: 上限のないジョブが、固まったまま既定の上限(GitHub Actions では 6 時間)まで走る。

### 6. 構造

- 判断や分岐を含む処理は、リポジトリのスクリプトに出し、ステップはそれを呼ぶだけにする。
  ステップに直接書くのは数行の呼び出しまで。
- ワークフロー・ジョブ・ステップには、何をするかが分かる名前を付ける。
- 必須チェックとして登録されたジョブの名前を変えない。変えるときは、必須チェックの設定と
  同時に変える変更として扱う。
- 複数のワークフローで繰り返す並びは、基盤の再利用の仕組み(再利用ワークフロー、
  複合アクションなど)に寄せる。コピーしない。
- 契機は必要なものだけにする。パスで絞った契機を必須チェックと組み合わせるときは、
  絞られて走らなかったときに必須チェックが待ち続けないことを確かめる。

スクリプトに出す理由: スクリプトはローカルで実行でき、テストでき、CI 基盤を替えても残る。
YAML の中のロジックは、push しないと試せず、基盤に閉じ込められる。これは
ba0918-verification の「ワークフローの文面ではなく、それが呼ぶヘルパーを実行して検証する」と
整合する。

合格条件: 上の 5 点が述べられている。
反例: 数十行の分岐を含むシェルをステップに直接書く。

## 判断と例外

- 規約が決めない細部(ファイルの分け方、ジョブの並び)は、そのリポジトリの既存の形に揃える。
  既存の形がないときは、`references/` の雛形に揃える。
- 外部の action を足す前に、数行のスクリプトで済まないかを考える。外部の依存は 1 つ増えるごとに
  固定と更新の対象が増え、供給網の入口が増える。採用か自作かの判断そのものは
  ba0918-reuse の領域で、ここでは CI 特有の重み(秘密情報のある文脈で動く)を判断材料に加える。
- 基盤が提供する公式の action(GitHub Actions なら `actions/` の下)も固定の対象から外さない。
  公式でもタグは付け替えられる。
- 基盤が規範を強制できるとき(固定を求める組織ポリシー、保護された環境、ランナーが検証する
  ロックファイル)は、文面の規範より強制のほうが強い。ただし、プレビュー段階の仕組みを
  採用するかはプロジェクトの判断である。

合格条件: SKILL.md の判断基準の節が、上の 4 点を述べている。

## 完了時の証拠

- 変更したワークフローに対する、基盤のワークフロー検査ツールの出力
- 変更したワークフローに対する、セキュリティの静的検査ツールの出力
- 変更したワークフローの外部参照を検索して、タグやブランチで指したものが無いこと
- 変更後の実際の実行結果(実行のリンクと結論)。push できない環境では、そのことと未確認の範囲を報告する

ツール名は基盤ごとに違うので SKILL.md には書かず、`references/github-actions.md` に
書く(GitHub Actions では actionlint と zizmor)。

合格条件: SKILL.md の証拠の節が上の 4 点を観測できる形で求めている。

## 既存スキルとの境界

- ba0918-secrets: 認証情報の見分け方、ステージングの禁止、漏洩時の初動。この規約は、
  パイプラインの中で秘密情報をどこまで渡すかだけを定める。漏洩したときの対応は secrets に従う。
- ba0918-release: 版番号、bump、タグ、変更履歴。この規約はリリースを行うパイプラインの
  書き方(キャッシュを復元しない、権限を絞る)を定め、リリースの規律そのものは扱わない。
- ba0918-verification: 検証の証拠の求め方。CI の定義のテストの仕方(文面ではなくヘルパーを
  実行する)は verification の例に既にあり、この規約は「ロジックをスクリプトに出す」側から
  それに整合させる。
- ba0918-reuse: 採用か自作かの判断。外部の action の採用もこの判断の対象である。
- ba0918-commit: CI の定義を変えたコミットの分け方と文言。

統合しなかった理由: `skill-authoring-rule.md` 規範 1 の基準を当てた。CI の定義を書く作業は、
上のどのスキルが読まれる作業とも一致しない。secrets に入れると常時読まれるスキルが膨らみ、
CI に触れない作業すべての読み込み量が増える。release に入れると、リリース以外の CI
(PR の検証)を書くときに読まれない。

## リポジトリへの組み込み

- `skills/ba0918-ci/SKILL.md` と `skills/ba0918-ci/references/github-actions.md` を追加する
- README と README-ja のスキル表に 1 行(Loaded by 列は `required:ci`)
- CHANGELOG の Unreleased に追加の記載
- `repository-design.md` の「初期スキル」表に 1 行
- `.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の description に、
  同じ文字列で CI ワークフローを足す。plugin.json の keywords に `ci` を足す
- このリポジトリの AGENTS.md のルーティング表に `ci` の行を足す
- このリポジトリ自身のワークフローをこの規約に合わせる(action のハッシュ固定、
  チェックアウトの認証情報を残さない、ジョブの上限時間、古い実行の取り消し、
  action の自動更新の設定)。規約を配る側が満たしていない状態で配らないため

## 受け入れ確認

- 人による確認: SKILL.md を、この仕様の各節の合格条件と 1 つずつ突き合わせる
- 既存チェッカー: `python3 scripts/validate.py` と pytest、CI の skills-ref が通る
- このリポジトリのワークフローに対する actionlint と zizmor の出力に、指摘が残っていない

この規約を機械検査するルールはバリデータに足さない。

## 作らないもの

- 特定の言語やビルドツール向けのワークフローの雛形集
- 実行環境(ランナー)の構築、組織ポリシーの設定手順
- 依存更新ツールやロック生成ツールのコマンド・フラグの詳細(変わるため)
- 秘密情報の漏洩対応の再掲

## 却下

- `ba0918-github-actions` という名前で GitHub Actions 専用に書く — スキル本文は特定のツールに
  依存させない規約(`skill-authoring-rule.md` 規範 3)に反し、他の基盤を使う日に二重化する
- 既存スキル(secrets / verification / release)への分散 — 1 つの作業で読むべき規則が散らばり、
  「作り方が毎回変わる」を解けない。「既存スキルとの境界」の統合しなかった理由
- ファイル名・ジョブ構成(lint → test → build など)まで規範で固定する — プロジェクトごとの
  事情とぶつかる。既存の形に揃える規範と、references の雛形で足りる
- GitHub のロックファイル形式を必須にする — プレビューで、形式もコマンドも変わると明記されている
- `always` のルーティング / ルーティングなし — 「発火条件」の節
