# 変異テストの運用の規約(ba0918-mutation-testing)

## 目的

変異テスト(実装に小さな変更 = 変異を1件ずつ入れ、テストがそれを捕まえるかを見る検査)は、
テストが本当に振る舞いを見ているかを機械で確かめられる数少ない手段である。一方で、
コストは「変異の数 × テストスイート1回の時間」で、素朴に回すと次の実害が出た。

- LLM が少し実装するたびに変異テストの完了を待ち(1回約2時間)、作業時間の9割が待ちになった。
  push 前のフックで差分を回していた kotowari では、push のたびに1〜2時間止まった。
- 負荷が高すぎて WSL ごと落ちた。CPU 使用率が100%に張り付き、同じマシンの他のセッションが
  止まり、ホストの PC が固まった。メモリを食い尽くす変異(無限に確保する、子プロセスを残す)もあった。
- 同じマシンの中で同時に回す変異の数を上げると、かえって遅くなった。kotowari の実測
  (2026-10-04、同じ44件)で、1件ずつ312秒、3件ずつ348秒(偽の時間切れ1件)、4件ずつ380秒。
  変異ごとのビルドが CPU を取り合う。
- CI に移したところ、メモリ上限を掛けずに回した分担が、時間切れの変異の直後にランナーごと
  落ちた(推測。ログは「runner has received a shutdown signal」)。同じ実行の他の分担は、本物の
  見逃しで失敗しており、「CI で落ちた」の中身が分担ごとに違った。

同じ相談が、プロジェクトと言語を変えて何度も繰り返された。対処の多くは道具に依らない
(資源の隔離、範囲の段、回す場所、関門の形)。この規約は、その道具に依らない部分を規範とし、
道具や OS ごとの具体的な書き方を `references/` に分ける。

## 発火条件

ルーティングのメタデータは `ba0918-routing: required:mutation` を宣言する。
生成される AGENTS.md のルーティング表に `mutation` の行として現れる。

発火させる場面:

- プロジェクトに変異テストを導入する、または設定・スクリプトを変える
- 変異テストを手元で回す、CI やフックに載せる、回す範囲や頻度を決める
- 変異テストの見逃し・時間切れ・失敗した実行を調べる
- 等価な変異を一覧に足す、または一覧を見直す

`always` にはしない。変異テストに触れない作業にまで読ませる理由がない。
ルーティングなし(description による発火だけ)にもしない。エージェントは「テストを回す」
つもりで変異テストを走らせることがあり、そのとき資源の隔離を読まずに走らせると、
マシンごと止める実害がある。AGENTS.md の表に行を出して名指しする。

## 対象

変異テストを走らせること全般: どこで(手元、フック、CI、定期実行、リリース)、
どの範囲を(差分、全体、ファイル単位)、どの資源の枠の中で、どの速さの工夫で回し、
結果をどう関門にするか。

扱わないもの: 個々のテストの書き方(ba0918-testing)、テストを先に書く順序(ba0918-tdd)、
CI の定義の書き方そのもの(ba0918-ci)、変異テストの道具の選定(ba0918-reuse)。

規範は道具と OS に依らない言葉で書く。具体形は次の references に置く。

- `references/resource-bounds.md`: Linux の cgroup(systemd-run)、コンテナ、WSL での資源の枠の掛け方
- `references/cargo-mutants.md`: Rust の cargo-mutants での具体形

他の道具(Stryker、PIT、mutmut など)が要るようになったら、同じ形でファイルを足す
(`skill-authoring-rule.md` 規範 2・3・4)。

## 規範

各節の合格条件は、SKILL.md の必須ルールの節がその規範を述べていることを指す。

### 1. マシンを守る

- 変異テストの実行は、プロセスの木全体のメモリと CPU に上限を掛けた枠の中で走らせる。
  上限の無いシェルから直に走らせない。
- 他の作業と同じマシンで走らせるときは、CPU と I/O の優先度を下げる。
- 変異1件ごとに実行時間の上限を掛ける。上限は、変異を入れない基準の実行の時間から決める。
- 打ち切られた変異が残したプロセスは、次の変異に進む前、または実行の終わりに必ず刈り取り、
  刈り取った数を報告する。
- 仮想化された開発環境(WSL、VM)では、環境の内側の枠に加えて、ホストの側からも環境全体に
  上限を掛ける。
- CI でも手元と同じ枠を掛ける。

内側の枠は仮想環境を守り、ホストを守れるのは外側の上限だけである。WSL ごと落ちた事例と、
ホストが固まった事例は、内側の枠だけでは防げない。

合格条件: 上の 6 点が述べられ、SKILL.md 本体に置かれている(マシンを止める実害に関わる
即応部分なので `references/` へ移さない。コマンドの具体形だけを references に置く)。
反例: メモリの上限だけを掛け、CPU の占有を許す。
反例: CI のランナーにユーザーの systemd が無いことを理由に、枠なしで走らせる。

### 2. 速さは決まった順で得る

- まずテストスイート自体を速くする。実時間を待つテスト(sleep、実際に経過させるタイムアウト、
  遅いサーバー)を書かない。待ちは注入し、仕様上の値は定数として検査する。
- 次に、道具が対応していれば、変異ごとに、その変異を観測しうるテストだけを走らせる。
  ただし採る前に、同じ範囲で全テストを走らせたときと見逃しを比べる。
- 次に、別々のマシンに分ける(分担)。
- 同じマシンの中で同時に回す変異の数を上げるのは最後で、同じ変異の集合で測って速くなったとき
  だけ。ビルドの並列数 × 同時の変異の数を、コア数を超えない値にする。

合格条件: 上の 4 点が順序とともに述べられている。
反例: 測らずに同時の変異の数をコア数に合わせて上げる。

### 3. 範囲を段に分ける

- 関門(マージを止める検査)の範囲は、基準との merge-base からの差分に入る変異にする。
- 全体は定期実行で回し、見逃しは関門にせず課題(issue など)として残す。
- リリースは、1つ前のリリースからの差分(前のリリースが無ければ全体)。
- 手元では、テストを書いている関数やファイルに絞って回す。

差分だけでは、変更していないコードの見逃し(そのコードの変異を捕まえていたテストを消す・
弱めると生まれる)が見えない。定期の全体実行はその穴を埋めるためにある。

合格条件: 上の 4 点と、定期の全体実行が要る理由が述べられている。
反例: PR ごとに全体を回し、待ちを理由に関門を外す。
反例: 差分の関門だけで、全体を一度も回さない。

### 4. 回す場所と待ち方

- コミット前・push 前のフックでは回さない。
- エージェントは、実装の1サイクルの中で変異テストの完了を待たない。手元で回すときは
  背景で走らせて別の作業を続けるか、CI に任せる。
- 関門は PR(マージ前)の必須チェックに置く。必須チェックの名前は分担の数から切り離す。
- CI のジョブの時間の上限は、分担あたりの変異の数 ×(ビルド + 基準のテストの時間)に余裕を
  掛けた見積もりから決める。

合格条件: 上の 4 点が述べられている。
反例: 「実装 → 変異テストの完了を待つ → 次の実装」を1サイクルにする。

### 5. 関門の形

- 関門は「範囲の見逃しが0件(等価として申告した分を除く)」にする。スコアの割合を閾値にしない。
- 等価な変異(入れても観測できる振る舞いが変わらない変異)は、理由を必須にした一覧で申告する。
  一覧に足す前に、コードを単純にして変異そのものを無くせないかを見る。足すときは、
  別の文脈のレビュアーに反証を試みさせる。外した件数を毎回出力する。
- ソースの中の除外の注記と、道具の除外設定は使わない。関門はそれらを見つけたら失敗する。
- 走り切らなかった実行(中断、基準の実行の失敗、道具の内部の誤り)は失敗として扱う。
  途中までの結果で合格にしない。結果のファイルは毎回作り直す。
  対象候補が0件で正常終了した実行は、同じ範囲・同じ分担で候補0件を確認した証拠が
  ある場合に限り、結果ファイルが無くても合格にできる。
- 道具の版を固定する。
- 基準の実行が通ること、不安定なテストが無いことを前提にする。
- 時間切れは見逃しと分けて報告する。同じ場所で時間切れが続くときは、テストが実時間を
  待っていないかを直す。

合格条件: 上の 7 点が述べられている。
反例: 「変異スコア80%以上」を関門にする。
反例: 見逃しを消すために、ソースに除外の注記を足す。

## 判断と例外

- 失敗した変異テストのジョブは、まず種類を見分ける: 見逃しで落ちた(関門が働いている)、
  ランナーごと落ちた(資源の枠が無い)、ジョブの時間の上限に達した(分担の見積もりが足りない)。
  回す場所を変えるのは、この見分けの後にする。
- 枠の大きさ(メモリの上限、CPU の割合)は数値で規範にしない。マシンと用途で変わる。
  references に初期値の目安だけを置く。
- 変異ごとのテストの絞り込みは、道具が対応していても既定にしない。比べてから採る。
- 等価の判断は人か LLM の申告で、機械では確かめられない。だから歯止めを重ねる
  (理由の必須、単純化の先行、反証、件数の出力)。

合格条件: SKILL.md の判断基準の節が、上の 4 点を述べている。

## 完了時の証拠

- 枠: 実行中のプロセスが枠の中にいることを示す出力(cgroup の所属と上限の値など)
- 速さの選択: 同時の変異の数や絞り込みを変えたなら、同じ変異の集合での比較の測定値
- 関門: 実際の実行の結果(見逃し・時間切れ・等価として外した件数)。CI ならその実行のリンク
- 抜け道: 除外の注記と除外設定を検索した結果、何も無いこと

合格条件: SKILL.md の証拠の節が上の 4 点を観測できる形で求めている。

## 既存スキルとの境界

- ba0918-testing: テストが振る舞いを見ているか(モックへの断言など)。見逃しの原因の多くは
  ここにあるが、この規約は見逃しの見つけ方と関門を扱い、テストの書き方は testing に従う。
- ba0918-tdd: テストを先に書く順序。変異テストは順序を問わない。
- ba0918-ci: CI の定義の書き方(固定、権限、時間の上限を置くこと)。この規約は、変異テストの
  ジョブに特有の上限の見積もり方と分担を定める。
- ba0918-verification: 検証の証拠の求め方。この規約の証拠の節はその具体化である。
- ba0918-reuse: 変異テストの道具の採用。

統合しなかった理由: `skill-authoring-rule.md` 規範 1 の基準を当てた。変異テストを回す・
載せる作業は、上のどのスキルが読まれる作業とも一致しない。testing に入れると、テストを
書くたびに運用と資源の話を読ませる。ci に入れると、手元で回すときに読まれない
(マシンを止める実害は手元で起きた)。

## 作らないもの

- 言語ごとのテストの速くし方の手引き
- 道具ごとの全オプションの解説(変わるため。規範に対応する部分だけを references に書く)
- 変異テストの道具そのもの、結果を読む道具

## 却下

- 道具ごとのスキル(`ba0918-cargo-mutants` など) — スキル本文を特定のツールに依存させない
  規約(`skill-authoring-rule.md` 規範 3)に反し、規範の大半が道具に依らない
- 変異スコアの閾値を関門にする — 弱いテストを足して稼げる。差分の見逃し0件の方が
  何を直すべきかが明確
- CI で回さず手元だけにする — 待ちを嫌って省かれ、関門でなくなる
- 枠の数値(メモリ何 GB、CPU 何%)を規範にする — マシンと用途で変わる
- `always` のルーティング / ルーティングなし — 「発火条件」の節
